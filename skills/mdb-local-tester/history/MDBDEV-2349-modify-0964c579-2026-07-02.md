## Что изменилось в коде mdb-data

1. **`KafkaClusterDiffDetector.hasBrokerConfigDiff`** — добавлен null-check для `brokerConfig()`:

```java
public static boolean hasBrokerConfigDiff(
    ModifyKafkaClusterParams newParams,
    KafkaClusterParams currentParams
) {
    final var newBrokerConfig = newParams.kafkaParams().brokerConfig();
    final var currentBrokerConfig = currentParams.getKafkaParams().brokerConfig();
    final var newConfig = newBrokerConfig != null ? newBrokerConfig.config() : null;
    final var currentConfig = currentBrokerConfig != null ? currentBrokerConfig.config() : null;
    return !Objects.equals(newConfig, currentConfig);
}
```

Раньше было `currentParams.getKafkaParams().brokerConfig().config()` — NPE, когда в БД `kafkaParams.brokerConfig` отсутствует.

2. **`KafkaClusterModificationValidator.validateConfigKeys`** — аналогичный null-check:

```java
final var brokerConfig = kafkaParams.brokerConfig();
if (brokerConfig != null && brokerConfig.config() != null) {
    final var config = brokerConfig.config();
    // ...
}
```

3. **`@Nullable` на поле `brokerConfig`** в:
- `ModifyKafkaParams` (api module) — DTO request
- `KafkaParams` (model module) — модель из БД

Раньше поле было без `@Nullable` в `@NullMarked`-классе, хотя по факту может быть null (старые записи в БД).

## Особенности

1. **`updateControllerConfig` запустился с пустым `parameters={}`** — потому что в done-версии 136662 `controllerConfig` отсутствовал (null), а в modify-запросе передали `controllerConfig: {config: {}}`. `hasControllerConfigDiff` сравнивает `null != {}` → true. Workflow делает upsert пустого конфига в PMS и рестарт 4 controller-инстансов (включая `nc`, которого нет в `controllerDcs=["hc","kc","zc"]` запроса — `nc` взят из `host_state`). Это может быть избыточно — хотелось бы не запускать updateControllerConfig при пустом `controllerConfig`.

2. **`updateBrokerConfig` запустился** — потому что в done-версии `brokerConfig` отсутствовал, а в modify-запросе передан с 3 ключами. Ожидаемо.

3. **`updateCruiseConfig` запустился** — `cruiseUpdateConfigData != null` потому что `cruiseControl` в modify-запросе != null. Это **не зависит от `hasCruiseControlDiff`** — workflow запускается по факту наличия `cruiseControl` в запросе. Важно для MDBDEV-2349: capacity update запустится, даже если поля cruiseControl совпадают с БД.

4. **Capacity update** — `cruiseUpdateConfigData` в этом запуске не содержал `diskGb/lanInMb/lanOutMb` (Jackson опустил null-поля), значит `brokerResources=null` → `upsertCruiseControlCapacity` делает Skipping. Это ожидаемо: broker resources diff=false.

5. **Controller рестартит `nc`** — в modify-запросе `controllerDcs=["hc","kc","zc"]`, но `updateControllerConfigData.controllers` включает `nc`. Список берётся из `host_state` (все controller-инстансы кластера), а не из `controllerDcs`. Похоже на поведение "обновить все инстансы контроллера".
