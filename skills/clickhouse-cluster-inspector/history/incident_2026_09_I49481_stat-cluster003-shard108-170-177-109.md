# I49481 — stat-cluster003-mytracker-ch: shard108 (пустые БД), shard170 (part intersects, краш-луп), shard177 (Code 160), shard109 (PREEMPTED)

Дата: 2026-09-02. Дежурный: Владислав Ершов. Кластер: `stat-cluster003-mytracker-ch` (mytracker, 192 шарда × 3 реплики dc/hc/rc, CH 22.3, политика `hybrid`: default=NVMe /var/lib/clickhouse/2, cold=HDD /var/lib/clickhouse/1).

## shard108-hc — хост поднялся с пустыми БД

**Симптом**: `1.shard108-db.stat-cluster003-mytracker-ch.hc` RUNNING, но 0 таблиц; distributed-запросы, попадающие на реплику, теряли данные шарда.

**Причина**: house-restore (`/usr/scripts/restore/restore_ch.py` + `restore-ch.service`) сломан ~с 21.04.2026: скрипт rsync'ит бэкапы из `rsync://<replica>:873/clickhouse-hdd/backup/` в `/var/lib/clickhouse/1/backup/`, но модуль смотрит в `/1/backup` донора, куда бэкапы **не пишутся** — реальные лежат в `/var/lib/clickhouse/2/backup` (create-ch-backup → clickhouse-backup использует диск /2). Модуль пуст → `Last backup is None` → `skip restoring` → хост без схемы. Плюс в момент первого прогона rsync до dc рвался (`Connection reset by peer`).

**Фикс** (ручной повтор флоу скрипта):
1. Скопировать свежий metadata-бэкап `2026-09-02T10-00-01` (3.3 МБ) dc → hc в `/var/lib/clickhouse/2/backup/<name>/` (mcc scp через ноут; модуль бэкапы не отдаёт).
2. Удалить устаревшие ZK-узлы старой реплики: на **восстанавливаемом** хосте (не на доноре!) выполнить 643 × `SYSTEM DROP REPLICA '1hc' FROM ZKPATH '/clickhouse/replication/stat.cluster003/shard308/mtp_olap2/<t>'`. Генерация: `SELECT concat(...) FROM remote('<dc-host>:9000', system, replicas, 'backup-admin', '<pass>')`.
   ⚠️ Грабля: `FROM ZKPATH` на доноре падает `Code 305 TABLE_WAS_NOT_DROPPED` («There is a local table ... use DROP TABLE or SYSTEM DROP REPLICA 'name' FROM db.table») — guard срабатывает, если на исполняющем хосте есть локальная таблица с этим путём. Выполнять на пустом хосте, либо с донора формой `FROM TABLE`.
3. На hc: `clickhouse-backup restore --schema --rbac '<backup>'` → 794 таблицы за 6 мин, репликация сама начинает тянуть данные (643 replicated-таблицы, ~8.3 ТБ, темп ~2.5 ГБ/мин → ~2 суток).
4. На время наливки исключить реплику из distributed: в PMS `zen.clickhouse.config.xml` (ключ `stat-cluster003-mytracker-ch.clouds`) `<priority>10</priority>` у 1hc-реплик shard108/shard170 + `confp --oneshot; SYSTEM RELOAD CONFIG` по всем 576 хостам.

**Follow-up**: тикет команде MDB — пустой rsync-модуль `clickhouse-hdd/backup` (house-restore не работает при пересоздании любого хоста кластера).

## shard170-hc — не вставал, `Part intersects previous part` (Code 49)

**Симптом**: краш-луп с 31.08. При старте/в очереди: `Code: 49 ... Part X intersects previous part Y ... bug or a result of manual intervention in the ZooKeeper data (LOGICAL_ERROR)` → `<Fatal>` → рестарт → 2-4.5 ч загрузки → снова Fatal. `force_restore_data` «не помогал» (см. выводы).

**Причина**: повреждён снапшот реплики `1hc` в Keeper (`/clickhouse/replication/stat.cluster003/shard370/.../replicas/1hc`) — в списке активных партов пересекающиеся диапазоны. Реплики dc/rc по тому же общему логу работают → лог консистентен, бит именно локальный снапшот (инцидент ~29-31.08: dc/rc рестартовались 29.08). Итог 15 битых таблиц (список ниже). Утяжеляющий фактор: на хосте с июня/июля две лишние БД — `mtp_olap2_replicated_subshard370` (794 replicated, свои ZK-пути) и `mtp_olap2_backup` (CollapsingMergeTree) → грузится 2410 таблиц вместо 794, старт 4.5 ч вместо 2.

**Ключевые наблюдения**:
- `force_restore_data` (в `/var/lib/clickhouse/2/flags/`, гибрид — флаг на диске 2!) подавляет проверку intersect **при загрузке** → сервер ДОГРУЖАЕТСЯ, но снапшот не чинит; после загрузки queue-потоки всё равно находят пересечения (`ReplicatedMergeTreeQueue::pullLogsToQueue → ActiveDataPartSet::add` → Fatal «Terminate called for uncaught exception», при этом процесс может выжить и заклинить — запросы не отвечают при живом порте).
- Uncaught-Fatal в фоновом потоке НЕ всегда убивает сервер → «живой но wedged» (SELECT uptime() таймаутит). Лечится только рестартом.
- Партиции/парты при intersect: например `202608_310_315_1` ⊃ `202608_310_314_2` — новый мерж-результат + старый парт в снапшоте.

**Фикс** (сервер wedged → offline-вариант):
1. `systemctl stop mdb-clickhouse-server` на hc.
2. С живой реплики (dc): 15 × `SYSTEM DROP REPLICA '1hc' FROM TABLE mtp_olap2.<t>` — чистая ZK-операция, форма `FROM TABLE` не упирается в guard. Возможно подвисание команд — ретраи; повторный прогон молча OK.
3. `systemctl start` → все таблицы грузятся, 15 битых цепляются свежими узлами и пересобирают снапшот из лога; локальные парты сверяются, недостающие фетчатся.
   Online-вариант (если сервер отвечает): по каждой битой таблице `DETACH TABLE; SYSTEM DROP REPLICA '<replica>' FROM ZKPATH '<path>'; ATTACH TABLE;` — без рестарта.

**15 таблиц**: appUserLaunchesFlowMobileVkma, appUserRegistrationsMgs, attrFirstLaunchesAtMobileVkma, customEventsAtWeb, customEventsLtWeb, devicePreFraudBitmap, launchesAtWebVkma, platformUserCustomEventsFlowWebVkma, platformUserFirstEventsMgs, segmentUsers, sessionFirstHitsAtWeb, sessionFirstHitsLtWeb, userCustomEventsLtWeb, userLaunchesLt, reengagementsFlowWeb (последняя проявилась только в queue-фазе — список из err.log может быть неполным, добирать по новым ошибкам).

**Follow-up**: после сходимости снять `<priority>10</priority>` и убрать force_restore_data; с юзерами обсудить снос `mtp_olap2_*_subshard*`/`mtp_olap2_backup` (рестарты 4.5 ч vs 2 ч).

## shard177 (rc) — дашборд-запрос «х5 медленнее», Code 160

`Estimated execution time 4240s > 3600. Estimated rows 172M. While executing MergeTreeThread` — запрос **отвергается до исполнения** (нагрузки в метриках нет вообще). Причина: партиция customEventsFlow 202608 на реплике уехала на HDD (`cold`): парты `20260801_20260831_3334_16639_6` (128 GiB) + `20260801_20260807_0_3333_5` (32 GiB); CH оценивает HDD-чтение пессимистично (~40k строк/с). Распределение по томам — per-host (move_factor, NVMe забит другими таблицами): на dc ещё 132 GiB этой таблицы на NVMe → тот же запрос туда проходит, балансировка кидает случайно. Рекомендации: поднять/выключить `max_estimated_execution_time` для дашборд-профиля; `MOVE PARTITION TO VOLUME 'hot'` НЕ делать (на rc NVMe свободно 213 GiB — не влезет); среднесрочно — тюнить move_factor/max_data_part_size_bytes политики hybrid.

## Общие грабли сессии

- mcc sshexec: первая попытка часто падает — ретраи 3-5 с паузой; трейлер `*** Connection closed by remote host ***` в конце вывода ЛОМАЕТ детекцию успеха по grep «closed» — проверять по своему маркеру (`echo RELOAD_DONE`).
- mcc scp директорию: создаёт вложенный subdir с именем исходной папки — проверять структуру после копирования; `/tmp` хостами через scp не забирается — staging в /var/lib/... или генерить файл на месте (remote()).
- PMS `zen.clickhouse.config.xml` — общий property на все CH-кластеры (карта `<cluster>.clouds` → XML, у stat003 ~163 КБ, 192 шарда): правка = читать values.do → python-точечная замена (assert count==1) → update.do байт-в-байт (jq --rawfile) → верификация values.do → `confp --oneshot; SYSTEM RELOAD CONFIG` по хостам (576 шт ~20 мин при xargs -P 6).
- Релоад конфигов по всему кластеру: `mcc instances "%shard%-db.<cluster>.<dc>%"` по трём ДЦ → hosts_all.txt → xargs -P 6.
- CH 22.3: `system.zookeeper_connection` нет; формат PrettyCompactNoEscapes (не NoEscases); remote() удобен для генерации SQL с донора на пустом хосте.
