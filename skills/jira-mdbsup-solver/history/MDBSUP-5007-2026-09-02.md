# MDBSUP-5007: kafka-m2b — RF=1 в БД mdb-data при фактическом RF=3 (Debezium-топик)

**Дата:** 2026-09-02
**Кластер:** `kafka-m2b` (adtech, 6195dc89-89ec-483e-bf6c-abc842fbf8df)
**Тип:** кейс без кластерной специфики (правка прод-БД + разбор обратного синка)

## Суть

Топик `dibezium.bannerd.schemahistory` создан Debezium-коннектором в обход API. В Kafka
партиция реально RF=3 (Replicas 21004,20004,22004, ISR полный), но в прод-БД
`backstage_plugin_mdb.databases` (строка id=7317) в `settings.kafkaSettings.replicationFactor=1`
→ UI валидирует изменение топика по этому полю и требует RF≥3 → «Bad Request», менять
настройки топика через UI невозможно.

## Фикс

```sql
UPDATE databases
SET settings = jsonb_set(settings, '{kafkaSettings,replicationFactor}', '3'::jsonb),
    updated_ts = now(), updated_by = '<login>'
WHERE id = 7317 AND cluster_id = '<uuid>'
  AND settings #>> '{kafkaSettings,replicationFactor}' = '1';
```
(через docker cp + psql -f, BEGIN/COMMIT; Kafka не трогали вообще — фактическое состояние корректно).

## Почему обратный синк не починил сам (факты по прод-БД)

- Синк жив: за 7 дней 2016 kafka-топиков обновлены `updated_by=one-cloud-ops`
  (+ `service.mdb-processing` при modify-операциях).
- **Синк обновляет только config (retention и т.п.) и не пересчитывает replicationFactor**:
  126 топиков с RF≤2 обновлялись за 30 дней — RF остался 1/2.
- Данный топик one-cloud-ops не трогал с 2025-10-09 (возможен фильтр «внешних» топиков;
  создан `ops_refresh_api` 2025-09-08).
- Массовый скоп: **1104 активных топика с RF≤2** по всем kafka-кластерам (в основном
  девстенды: kafka-devstand 425, s3-scheduler-queue 297, kafka-dynstand 78; есть
  похожие на прод).

Гипотеза (код не читали — не подтверждено): refresh считает RF «управляемым» значением API
(RF меняется только операцией modify), поэтому не синкает его из Kafka. Проверить при
повторных кейсах по коду refresh-логики one-cloud-ops / mdb-data.

## Грабли/заметки

- Таблица топиков — `databases` (settings JSONB, `kafkaSettings.replicationFactor`);
  топики «в обход API» унаследуют RF на момент создания и никогда не пересинкаются.
- Кандидат на массовый тикет/скрипт: пересчёт RF из фактических assignments для 1104
  топиков (аккуратно: часть может быть реально RF=1 на девстендах — сверять с Kafka).

## Статус

RF исправлен 2026-09-02 (rf=3, верифицирован SELECT'ом), комментарий в тикете, тикет закрыт.

## Продолжение (2026-09-02, после закрытия): NPE при изменении топика через UI

Нанзутов попытался изменить retention через UI → 500:
`Cannot invoke "DatabaseSettings.kafkaTopicSettings()" because the return value of "KafkaTopic.getSettings()" is null`.

### Диагноз

- Stacktrace (mdb-data err.log, все ДЦ): `KafkaSyncController.syncKafkaTopics` →
  `KafkaSyncServiceImpl.syncKafkaTopics:178` → `settingsChanged:226`.
- Корень — прямо перед NPE в логе: Jackson
  `InputCoercionException: Numeric value (9223372036854776000) out of range of long
  (-9223372036854775808 - 9223372036854775807)`. Debezium создаёт schemahistory-топик с
  retention.ms=Long.MAX_VALUE (9223372036854775807 — в самом Kafka значение корректно),
  но при синке в БД значение теряло точность (double/JS) → в JSONB писалось
  9223372036854776000. Jackson не может распарсить его в Long → settings=null → NPE.
- Массовость: 13 строк `databases` (все — schemahistory-топики Debezium, updated_by
  ops_refresh_api) с retentionMs > Long.MAX_VALUE по всем kafka-кластерам.

### Фикс (по указанию пользователя; баг в коде уже пофиксен)

```sql
UPDATE databases
SET settings = jsonb_set(settings, '{kafkaSettings,config,retentionMs}', '9223372036854775807'::jsonb),
    updated_ts = now(), updated_by = 'vl.ershov'
WHERE is_deleted = false
  AND (settings #>> '{kafkaSettings,config,retentionMs}')::numeric > 9223372036854775807;
-- UPDATE 13, верификация: 0 сломанных осталось
```

Комментарий в тикет (retention исправлен, попробовать ещё раз). Детали SQL — здесь, не в тикете.

### Грабли/заметки

- JSONB numeric хранит точное значение — Jackson падает только при чтении в Java-модель
  (Long). UI показывал retention как 9223372036854776000 (106751991167d 7h) именно из БД.
- mdb-data err.log: ERROR-строки ControllerLogAspect БЕЗ timestamp — время события
  определять по соседним INFO-строкам; trace id UI в err.log отсутствует.
- `mcc sshexec` на kafka-брокере: kafka-configs.sh требует
  `--bootstrap-server $(hostname -f):9092 --command-config /opt/kafka/config/client.properties`
  + `unset KAFKA_OPTS JMX_PORT` (localhost:9092 без client.properties → TimeoutException);
  команды с кавычками в sshexec ломаются — через expect-heredoc (kafka-host-inspector).
