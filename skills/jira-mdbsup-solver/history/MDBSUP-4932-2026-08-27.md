## Главный паттерн: деплой переименовал workflow-тип → RUNNING-воркфлоу висят вечно

26.08 ~13:50 МСК деплой mdb-processing переименовал тип `downscaleKafkaController` →
`downscaleKafkaControllerInCluster`. Три уже идущих воркфлоу зависли навечно: каждый
workflow task падает `java.lang.Error: Unknown workflow type "downscaleKafkaController".
Known types are [...]` → `WORKFLOW_TASK_FAILED` без перепланирования, воркфлоу не может
ни продолжиться, ни упасть. Операции в БД in_progress ~сутки.

Признак в истории Temporal: события обрываются на `WORKFLOW_TASK_FAILED`, статусы
WORKFLOW_TASK до фейла — COMPLETED (деплой посреди исполнения).

Лечение: операции → `status='canceled'` (enum позволяет), пользователь перезапускает
delete_hosts — новый operationId = новый workflowId уже нового типа; conflict'а
ALREADY_EXISTS нет. Зомби-воркфлоу остаются RUNNING в Temporal (terminate через UI API
падает «missing csrf token») — вреда нет, но листинг загрязняют.

Что успевает флоу до зависания — смотреть по истории (quorum PMS, reload брокеров,
рестарт контроллеров, stop/withdraw): перед перезапуском проверять облако/`mcc instances`
и host_state — часть шагов уже сделана, при перезапуске флоу идемпотентен, но при уже
выведенном сервисе может скипнуть финальный save (не почистит host_state/controllerDcs —
см. target-11-dwh ниже).

## Доделка 28.08 (повторное обращение: «удаление не прошло»)

Пользовательские unregister/withdraw так и не состоялись: брокер 20001 оставался живым
и зарегистрированным (host active, api-versions показывает 20001/hc), а операция
c83e2fe6 висела failed с finished_ts=NULL → блокировала новые delete_hosts. Докончено
вручную по канону [4899](../../kafka-cluster-inspector/history/MDBSUP-4899-2026-08-27.md):
drain перепроверен (kafka-log-dirs по broker-list 20001 → 0 партиций, bootstrap только
через FQDN живого брокера — localhost:9092 на hc не отвечает; вывод в ANSI — грепать
`^{"brokers`), unregister kafka-cluster.sh --id 20001, mcc stop/withdraw service+storage
(hc), UPDATE c83e2fe6 → done. Урок: «докончено пользователем» надо верифицировать
тем же днём — иначе остаётся failed-операция-блокиратор + живой выведенный из host_state
брокер (CC может вернуть на него партиции).

## Грабли/заметки

- `mcc ops` для очереди кластера отвечает по любому `-c <dc>` — брать ДЦ удаляемого хоста.
- Подсчёт партиций по всем топикам на прод-кластере (300+ топиков) не влезает в expect
  timeout — только nohup на хосте + повторный заход за результатом.
- Temporal UI API terminate требует csrf — недоступен из CLI; только чтение.
- У dwh-кластеров в host_state после downscale контроллера остаются broker.hc — их
  удаляют отдельной операцией (возможно, заблокированной до закрытия текущей).
