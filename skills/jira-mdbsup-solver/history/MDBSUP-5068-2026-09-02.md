# MDBSUP-5068 — «отрыв» прав пользователя при редактировании доступов (2026-09-02)

Кластер: oneme Kafka `14aa4059-4d9c-4cd3-a852-35d3e06629f9`, юзер `dwh_rt_antifraud_reader`.

## Суть

Права на топик `oneme_antispam_pr_idsSpamAction` (выданы в 14:51, операция `441224de`)
пропали после выдачи прав на группу в 16:32 (`914e5927`), вернули в 17:48 (`5cd87258`).
Все операции `update_user`, все `done`, созданы самим заявителем (a.perevalov) — никто
чужой ACL не правил.

## Причина

**Обратный синк — это синк из Kafka в UI.** `update_user` несёт **полный** список ACL
пользователя (desired state), UI берёт его из обратного синка (Kafka → UI) на момент
открытия диалога. Если диалог открыт до применения предыдущей операции, снапшот
устаревший — сохранение перезаписывает свежие ACL (last-write-wins). Доказательство:
в модели операции 16:32 нет 4 ACL на `idsSpamAction`, которые были в модели 14:51;
вернулись в 17:48. Тот же паттерн днём раньше: 14:38 → 151 ACL, 14:51 → 36 (−144/+29).

## Вывод для диагностики

Проверять `operations.operation_model->'kafkaUser'->'permissions'` последовательных
update_user: diff списков показывает, что именно «исчезло» — в БД это видно сразу,
Temporal/хосты не нужны.

## Баги

- **MDBDEV-3305** — обратный синк не синхронизирует ACL существующих пользователей
  (доказано дрейфом: в Kafka ~147 ACL у юзера, в БД permissions — 32; sync ходил
  каждые ~15 сек и ACL не переносил). Файл разбора приложен к тикету.
- UI-затирание ACL при долгоживущем диалоге (update_user = full overwrite,
  last-write-wins) — отдельный баг на mdb-data UI, не заведён (предложено в тикете).
