## Причина №1: рестарт «выполнился», но не применился → HOST_NOT_READY

Per-host ребёнок (ec_1): `kafka_host_restartBrokerInstanceSsh` → COMPLETED (быстро),
далее 11 × `pingSshRestartedBrokerInstanceReady` = false за ~13 мин →
`HOST_NOT_READY "ping is not ok"` (`KafkaHostWaiter`, workflow-retry, policy not set).
retry-политика activity — старая deploy-override 3/10s/120s (см.
temporal-worker/history/2026-08-27-upscale-kafka-controller-reload-failures.md).

Фактическое состояние хостов: все 6 брокеров **живы и active**, но:
- ec_1/ec_2/kc_1/kc_4: и конфиг, и JVM от 15:09–15:12 UTC (рестарт из предыдущей успешной
  add_hosts `6bb87c67`); рестарт run 2 их НЕ тронул;
- rc_2: конфиг отрендерен в 16:01 (= moment run 2), но JVM от 15:12 — работает со старым
  конфигом в рантайме.

Вывод: `confp --oneshot && systemctl restart` через sshExec вернул успех, но рестарт
физически не выполнился (systemd ActiveEnterTimestamp раньше); ping-воркер честно ждал
свежего рестарта → фейл. Т.е. HOST_NOT_READY после «успешного» рестарта = смотреть, что
реально произошло на хосте (lstart JVM vs время рестарта activity), а не считать хост
мёртвым. (Отличается от кейса 27.08: там restart падал по proxy `Invalid type of response`.)

Диагностика на хосте:

## Причина №2 (главная): контроллер pc не создан в облаке

`mcc --local -n infra -c pc status "controller.okfeed-eventstream-kafka"`:
инстанс `1.controller.okfeed-eventstream-kafka.pc.one-infra.ru` — state NEW,
availability UNAVAILABLE, с 18:15 МСК; progress: «(CREATE_FAILED on srvm4536) is not
ready to mount».

Volumes (`tool_status --type storage "<queue>/controller"`):
- data uuid `2d4db6f6-a22a-11f1-9006-35da0901cafd`: CREATE_FAILED —
  `mount(2) failed: Structure needs cleaning` (mount code 32, битая ФС, minion srvm4536);
- logs uuid `2d4db6f7-a22a-11f1-9006-35da0901cafd`: CREATE_FAILED «Cancelled due to data
  create failure».

Т.е. «контроллер создан успешно» в тикете — только про workflow-фазу; облако хост не
развернуло, run 2 его не ждал (скип за 0.6с). Брокеры уже работают с voters, включающим
`14001@1.controller...pc:9093` (voters не менялся между версиями конфига — менялось что-то
ещё, 7225→7290 байт), кворум 3-4 из 4 живых, кластер работает.

## Решение (согласовано с пользователем)

Пересоздание volumes своими руками отложено: комментарий в тикет — ждать выхода из
CREATE_FAILED (само / дежурные облака), затем перезапустить add_hosts (прогонит reload
всех 24 брокеров, дообновит 6 отстающих конфигов, вставит pc в host_state, done).

Если пришлось бы чинить самим: lifecycle (stop → delete volumes `2d4db6f6-…,2d4db6f7-…`
→ start → purge) — данных нет (контроллер ни разу не поднимался), кворум dc/ec/kc/rc жив,
безопасно.

## Грабли/заметки

- Workflow-фаза `_pc` COMPLETED ≠ хост создан: при идемпотентном скипе run 2 облако могло
  даже не начать деплой. Всегда сверять `mcc status`/`instances` фактическим состоянием.
- `attempts_left=0` + `in_processing=t` у failed-операции — живого workflow нет (проверено
  listing'ом Temporal), правки/рестарт безопасны.
- error_message «Config reload failed for hosts: […]» перечисляет хосты из ВСЕХ ДЦ — не
  верить локализации из описания тикета (в тикете были только EC; фактически ec/kc/rc).
