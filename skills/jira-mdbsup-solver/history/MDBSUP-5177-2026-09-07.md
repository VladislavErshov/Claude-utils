# MDBSUP-5177 — logs (adtech/kafka): delete_hosts kc-брокера «зависло» на get_kafka_downscale_broker_result (07.09.2026)

Кластер `db9d2180` (logs-adtech-kafka), операция `aa8bbd21` delete_hosts — вывод **2.broker...kc (21002)**,
`--cloud=kc --replicas=1` (НЕ последний брокер в ДЦ). mdb-data поллит get_result (need_retry,
~90 мин/попытка). Тикет создан через 2 ч после старта — «висит». Разбор: не зависание —
штатный медленный drain, тот же подтип «задача живая, ведёт перелив сама», что dzen-comments2
в [MDBSUP-5103](../../../kafka-cluster-inspector/history/MDBSUP-5103-2026-09-03-mass-datatransfer-delete-hosts.md).

## Отличия/дополнения к 5103

- **Downscale не последнего брокера** тоже живёт в операторе (get_result ждёт исчезновения
  задачи), но `isWithdrawing=false` — withdraw service/storage не нужен, после drain оператор
  только разрегистрирует брокера. Вручную делать нечего вообще.
- **Медленный drain больших партиций — не зависание**: access_log-0 (86 ГБ) и command_log-0
  (222 ГБ) переливались в uc по ~8 МБ/с → часы в «Waiting for broker reassignment check».
  Прогресс проверять: log-dirs size источника vs приёмника + Jolokia
  `ReplicationBytesInPerSec` на приёмнике (порт 7777). Успешный признак — партиция исчезает
  из log-dirs источника.
- **URP во время drain — транзиентный шум**: снапшот 83 URP, через 4 мин 0 (волна догоняющих
  реплик). О здоровье судить после повторной проверки.
- **Таймстемпы оператора (`alerts ... since`) и прод-БД (`operations/tasks`) — МСК, не UTC.**
  В тикете «ретраится с 13:21 UTC» было на самом деле 13:21 МСК = 10:21 UTC. Сверять с `date -u`.

Итог: тикет закрыт комментарием с диагнозом и ETA; операция должна сойтись сама ~21:30 МСК
07.09 (проверка сходимости в этот же вечер — при успехе фиксировать нечего, при failed — SQL done по шаблону 5103).
