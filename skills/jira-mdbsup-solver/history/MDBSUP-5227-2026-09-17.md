# MDBSUP-5227 (2026-09-17): dual-stack Redis year-mem-prod — запросы клиента уходили по IPv6

Кластер: year-mem-prod (`0cf8fdef-6f92-405a-a77b-f88484dfddb8`), проект vk-stories,
**ns=infra** (не vkontakte, как предполагал заявитель), шардированный, 3 шарда × 3 ДЦ
(ic/nc/zc), queue `year-mem-prod-vk-stories-redis`. Клиент v4-only (сервис ВКонтакте),
редиректы CLUSTER SLOTS/MOVED отдавали v6. Вопросы: перевод в v4-only + поддержка IPv6
в неймсейсе. operationId не при делах — зависших операций нет.

## Главное

Фикс по канону **MDBSUP-5442** (полный разбор —
`~/.claude/skills/redis-cluster-inspector/history/MDBSUP-5442-2026-09-17.md`):
`cluster-preferred-endpoint-type hostname` → редиректы отдают FQDN (A+AAAA), v4-only
клиент берёт A. v4-only штатно недоступен, hostname-режим — эквивалент.

## Уникальное в этом кейсе

1. **Фикс может быть применён частично — проверять ВСЕ 4 слоя фиксации, прежде чем
   чинить заново.** Здесь 3 из 4 уже были сделаны кем-то в рамках modify_cluster 15.09
   (runtime config set на 9 нодах, строка в redis.conf, PMS `zen.redis.conf`), а
   `cluster_to_template` (redis_cluster_config) забыли — при первом update через UI
   настройка слетела бы. Доделан только шаблон: `UPDATE cluster_to_template SET
   template_body = template_body || E'\ncluster-preferred-endpoint-type hostname\n'`.
2. Диагностика частичности: `ps` start time (рестартов не было) vs mtime redis.conf
   (рендер во время modify) vs `config get` (runtime) vs PMS values.do vs
   cluster_to_template — сверять послойно.
3. Неймсейс кластера уточнять в БД (`JOIN namespaces`), а не верить формулировке
   заявителя: «vkontakte» из тикета оказался ns=infra.

## Грабли

- Docker daemon подвис → psql из контейнера недоступен; DML и SELECT через
  `python3 + psycopg2` на туннель localhost:53480 (фоновый `mcc tp-port-forward` без
  nohup умирает при завершении shell-команды — стартовать через nohup).
- Туннель может «висеть»: tsh LISTEN есть, но psql хангует на SELECT 1 → kill и
  пересоздать.
