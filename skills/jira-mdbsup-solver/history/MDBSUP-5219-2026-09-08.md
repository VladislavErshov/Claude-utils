# MDBSUP-5219 — pub-processing (dzen): зависла sys_update_cluster (docker-образ)

Дата разбора: 2026-09-08. Кластер: `pub-processing` (Kafka, dzencontent), UUID `8191b27b-0593-44d7-a7fd-bec53d562bef`, очередь `pub-processing-dzencontent-kafka.dzencontent.db.production.mdb.prod`, ns dzen / домен idzn. Контроллеры dc/pc/rc + брокеры dc/pc/rc.

Операция `sys_update_cluster` `afe318c1-9298-45f7-ae5d-2f454eb23ab2` (d.shakurov, 08.09 15:02 МСК), ubuntu20-kafka-3.8.0 → 2.4.4 (в mdb-БД «текущий» был 1.1.3 — устаревший).

## Главное: dzen-кластеры НЕ в общем прод-Temporal

- Общий Temporal `mdb-processing-temporal.common.mdb.one-infra.ru` (ns default): по operationId/ClusterId/окну времени — пусто. dzen-кластеры обслуживаются **оператором one-cloud-ops** (`mcc ops "queue://<fullQueue>"`), а не mb-processing-workflow'ем в этом Temporal.
- Диагностика: прод-БД (`operations`, `one_cloud_meta` → fullQueue/domain) → `mcc -n dzen -c <dc> ops "queue://..."` → sshexec на хосты.

## Цепочка

1. mdb-операция запускает задачу оператора `kafka.update --db-type=kafka --image-version=2.4.4` (старт 08.09 15:03).
2. Задача ждала «instances to be RUNNING RESERVED»: контроллеры **pc/rc в RUNNING PREFAIL с 07.09 17:17:06** (до старта операции!), report `There are minimum controller count`.
3. `get_result_service_sys_update_operator` крутился в need_retry → операция позже сама перешла в **failed** (`Error while get_result_service_sys_update_operator: Operator task ... in progress undefined`, attempts_left=2, in_processing=false).

## Корневая причина

**Рассинхрон KRaft-кворума контроллеров.** В PMS `kafka.controller.quorum` на ключе `pub-processing-dzencontent-kafka.clouds` значение уже было правильное (3 voters: dc=10001, pc=12001, rc=13001), но на **pc/rc** контроллер-хостах `/opt/kafka/config/controller.properties` не был перерендерен после удаления старых хостов (05.08): там оставался старый сет из 5 voters с мёртвыми `11001@1.controller...hc` и `10002@2.controller...dc`. dc имел правильный конфиг (был leader). rscheck на pc/rc тоже держал старый список (`/etc/rscheck/kafka.conf`, ключ `controller_hosts`) и сыпал «Не удалось подключиться» / fatal `Can't create connection` (с 07.09) → one-cloud пометил оба контроллера PREFAIL → задача update встала навсегда.

## Что сделали (08.09 ~17:20–17:35 МСК)

1. Проверили PMS — значение правильное, **писать в PMS не потребовалось** (овнеррайдов на controller-ключе/per-DC нет).
2. На каждом контроллере по очереди pc → rc → dc (dc-лидер последним):
   `cp controller.properties в /tmp/controller.properties.bak.5219` → `confp --oneshot` → проверка строки `controller.quorum.voters` (стала 3 voters) → `systemctl restart kafka-controller` → проверка raft-state через jolokia `kafka.server:type=raft-metrics/current-state`.
3. **Грабля:** после confp рестартовать и `rscheck@kafka` — он не перечитывает kafka.conf на лету и продолжал генерить фейлы по старому списку. `systemctl restart rscheck@kafka` на всех трёх.
4. Результат: кворум собрался (лидер переехал на pc), алерт «Failed hosts» → «no failed hosts», **pc/rc вышли из PREFAIL в RESERVED**, задача `kafka.update` ожила и начала перекатывать брокеров на 2.4.4 (dc → pc → rc, «Updated clouds» рос).

## Хвосты / наблюдения

- На контроллер-хостах юнит `kafka-broker.service` enabled и failed с 04.08 (ExecStartPre падает — это норм для KRaft-контроллера, юниту там нечего стартовать). Остаточный алерт `failed-systemd-services: Required pattern 'ALL_SERVICES_OK' missing: kafka-broker.service` на pc/rc (и dc с 22.08). На PREFAIL после фикса кворума не влияет, но мусорит — кандидат на отключение юнита/правку чекера.
- Версия образа в mdb-БД (db_versions/«currentTag» 1.1.3) расходилась с фактической (брокеры 2.3.1, контроллеры 2.4.3) — из-за этого sys_update вообще был предложен как 1.1.3→2.4.4.
- Операция в БД осталась в failed; после завершения `kafka.update` состояние кластера/операции в mdb сверить, при необходимости ретрай sys_update_cluster (авторетрай attempts_left=2 может воткнуться сам).
- Полезное: вывод модели оператора — `mcc --local -n dzen -c <dc> ops "queue://<fullQueue>" -f json` → `.[0].alerts["kafka.update"]`, `.[0].operators.kafka.tasks.update`; состояния raft — jolokia `kafka.server:type=raft-metrics` на 7777 контроллера.
