# MDBSUP-5180 — vkmusic-common: add_hosts (controller ec) «Couldn't find workflow in processing to sync status» (07.09.2026)

Кластер `fb0120d6` (vkmusic-common-combo-kafka), операция `d5448c65` add_hosts (контроллер в ec).
Операция failed, `in_processing=true`, `attempts_left=0`; в Temporal workflow **вообще нет**
(ни по WorkflowId, ни по префиксу). Кластерная специфики нет (хосты не трогали) — полный разбор здесь.

## Причина

**DNS-аутедж на прод-хостах mdb-processing 12:41–13:21 МСК 07.09**: gRPC к Temporal frontend падал
`UNAVAILABLE: Unable to resolve host running.frontend.mdb-processing-prod-mdb-temporal.clouds.one-infra.ru`
(~17k ошибок на 1.hc, ~8.4k на 2.hc). Операция создана 13:19:16 — внутри окна; старт workflow
`upscaleKafkaController` не состоялся. В 13:21 DNS восстановился, все последующие операции проходили —
но retry **старта** не предусмотрен: mdb-data только синкает статус (WARN `Workflow execution not found`
в processing) и исчерпывает попытки. Blast radius — только эта операция.

## Диагностика (что где искал)

- Прод-БД: операция failed + `operation_model` (`dc: ec`) + в `host_state` ec-контроллера нет.
- Temporal API: `WorkflowId = '<opId>'`, `STARTS_WITH`, `ClusterId = ...` — пусто (только старые completed 01.09/03.09).
- ⚠️ **Логи processing с 05.09 лежат в `/mnt/logs/mdb-processing.app.log`** — `/one/logs/java.log`
  заморожен рестартом приложения 05.09 01:01 (fd 8 нового процесса → app.log; JFR при этом
  продолжает писаться в /one/logs). `/one/logs/systemd.log` — протухшая копия с 29.05, не источник.
  (prod-log-investigator обновлён.)
- Ошибка «Couldn't find workflow...» — это ответ синка mdb-data, не первопричина; первопричина
  ищется в app.log processing по маркеру `Unable to resolve host`.

## Отличие от MDBSUP-4752 (add_hosts stuck)

В 4752 workflow упал в середине — хост-сирота уже существовал в облаке, нужна была ручная вставка
в `host_state`. Здесь workflow не стартовал вовсе → хоста в облаке нет (`mcc instances` ec — пусто),
вставлять в host_state нечего; кластер живёт на 3 контроллерах (hc, pc, rc) без потерь.

## Действия

Только закрытие операции в прод-БД (по решению владельца — **canceled**, не done, т.к. ничего не сделано):

```sql
UPDATE operations SET status='canceled', in_processing=false, finished_ts=now(), error_message=NULL
WHERE id='d5448c65-9277-40f3-badb-74b66f70ef0a' AND status='failed';
```

Дальше пользователь повторяет add_hosts (controller, ec) в UI — новая операция стартует workflow с нуля.

## Продуктовый баг (пока не заведён — предложить)

Транзиентная недоступность Temporal на момент создания операции оставляет её навсегда сломанной:
UI-retry не пере-стартует workflow, а только дёргает синк статуса. Ждать: тикет в mdb-data/mdb-processing
(start-workflow должен ретраиться или операция — отменяться с возможностью явного рестарта).
