# MDBSUP-4899 — Kafka prod-stat-events: downscale-broker застрял в операторе (27.08.2026)

Кластер `prod-stat-events` `73d1e566-ab0c-4b21-880b-ca7d7fe4e1ab` (vk-support, ns infra,
fullQueue `prod-stat-events-vk-support-kafka.vk-support.db.production.mdb.prod`).
Операция `999b827d-61b0-4524-b685-a059e703595f` delete_hosts (26.08 14:08, удаление брокера hc)
failed на `get_kafka_downscale_broker_result`: «Operator task ... in progress [object Object]».
Temporal по operationId пуст (operator-флоу). Предыдущий delete_hosts hc (11c5c32b) прошёл
успешно; target = последний брокер в hc `1.broker...hc.one-infra.ru`, brokerId **21001**
(dc=20001, ec=23001, rc=22001).

## Диагностика

- `mcc ops`: `kafka.downscale-broker --cloud=hc --replicas=0` висит с 26.08 14:09,
  state: isWithdrawing/serviceWithdrawn/storageWithdrawn = false (задача НИЧЕГО не сделала).
  precondition false: `isReadyForActions() false` + `kafka.watch[refreshAvailabilityState]:
  'No one primary in cluster'` — при этом Jolokia на контроллерах: rc=leader, dc/ec=follower
  (кластер жив; «No one primary» = артефакт модели оператора, как в MDBSUP-4895).
  Отличие от 4895: ghost-хостов нет (instances().count()==getNodes().size()==8).
- Клиентские шаги до оператора (modify_kafka_hosts, update PMS quorum) уже прошли —
  host_state в БД уже без hc-брокера; брокер остался только в облаке + метаданных Kafka.

## Лечение (вручную по шагам оператора)

1. Убедиться: нет RUNNING-ретрая (Temporal пуст, attempts_left=0).
2. `mcc op_stop "queue://<fullQueue>" kafka.downscale-broker` — СНАЧАЛА, чтобы не гонялся
   с ручными действиями (в 4895 останавливали в конце — лучше до).
3. Reassignment: по скиллу `kafka-reassign-partitions` собрали describe всех топиков
   (5 топиков, 129 партиций; база-чанковая заливка collect-скрипта на хост) —
   **ON_21001=0**: партиции уже перелиты (34/28/19/19/15/14 по перестановкам
   20001/22001/23001, ровно 1 реплика на ДЦ). Reassign не потребовался.
4. Unregister 21001: single-file Java (`Unregister.java`, AdminClient.unregisterBroker,
   client.properties юзер super), `java -cp "/opt/kafka/libs/*" Unregister.java <host>:9092 21001`
   на живом брокере → `UNREGISTERED=21001`. Проверка: api-versions показывает 3 брокера.
5. Withdraw в облаке: `mcc stop broker.prod-stat-events-vk-support-kafka` (-c hc) →
   FINISHED → `mcc withdraw --type service` (мгновенно) → подождать исчезновения инстанса
   (иначе `Cannot withdraw storage used by servises`) → `mcc withdraw --type storage
   "<fullQueue>/broker"` — уравнение 8-1 через pexpect-обёртку → «NON EMPTY ... PURGEABLE».
6. Верификация: downscale-задача TASK_ABSENT в `mcc ops`; контроллеры rc=leader.
7. Прод-БД (docker cp + psql -f, BEGIN/COMMIT):
   ```sql
   UPDATE operations SET status='done', in_processing=false, finished_ts=now(), error_message=NULL
   WHERE id='999b827d-61b0-4524-b685-a059e703595f' AND status='failed';
   ```

## Грабли этого кейса

- `mcc scp` (загрузка НА хост) молча не заливал файл (macOS-источник) — рабочий путь:
  expect + `printf %s '<b64-chunk>' >> /tmp/x.b64` чанками по ~800 символов.
- `mcc sshexec` с длинным аргументом (base64 в команде) → `414 URI Too Long` (команда
  уходит в URL). Только expect-ssh для заливки.
- Tcl expect падает на `[0-9]` в send (command substitution) — сложные команды только
  heredoc-скриптом на хосте.
- `kafka-topics.sh --describe` БЕЗ --topic даёт только сводку топиков (без партиций);
  партиции — только `--describe --topic <t>` по каждому (и `</dev/null` внутри while read,
  иначе скрипт съедает stdin списка топиков).
- `java Foo.java` (source-file mode) с kafka-классами: classpath обязателен, иначе
  «cannot find symbol AdminClient» — `java -cp "/opt/kafka/libs/*" Foo.java`.
