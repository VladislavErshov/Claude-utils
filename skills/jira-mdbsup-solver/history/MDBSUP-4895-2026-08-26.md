# MDBSUP-4895 — Kafka downscale-broker застрял в операторе one-cloud-ops (26.08.2026)

Два кластера mail застряли на `get_kafka_downscale_broker_result`. Выяснилось: операции
этого типа живут НЕ в Temporal, а в **операторе one-cloud-ops** (старый проект,
`/api/task/start` → задача `kafka.downscale-broker` внутри оператора).

|---|---|---|---|---|
| workspace-mail-kafka | 9769ce4b-0e39-43ea-8994-9d79c81a440d | 4af4a156-b149-4ac5-a456-5e7a530812a1 | hc, id 20001 | broker в ec/kc/pc |
| vahter-mail-mail-kafka | fb912cc0-4c60-4b29-b96c-11c31802fe83 | 2ecd2303-e36b-4eff-b70f-85e0ff1f2ce8 | kc, id 20001 | broker в ec/pc/rc |

## Диагностика

1. Temporal: workflow по обоим operationId **отсутствуют** (`{` на query WorkflowId) —
   значит это операторный флоу, не Temporal.
2. Прод-БД: операции `delete_hosts` `in_progress`/`failed`, `error_message` =
   «Operator task ... in progress [object Object]» (наш `GetResultOperatorTaskProcessor`,
   mdb-backend). DONE ставится только когда задача исчезает из `operators.kafka.tasks`.
3. `mcc ops queue://<fullQueue>` →alerts:
   - `kafka.downscale-broker: precondition() is false ... isReadyForActions() false`
   - `kafka.watch[refreshAvailabilityState]: Cluster is UNAVAILABLE, 'No one primary'`
   - vahter: ghost-хост `1.controller.vahter-mail-mail-kafka.kc` UNAVAILABLE с 17:20 —
     контроллера в облаке уже нет (EntityNotFoundException), модель оператора протухла.
4. Реально кластеры здоровы: Jolokia `kafka.server:type=raft-metrics/current-state` —
   лидеры есть (vahter: pc, workspace: kc). «No one primary» — артефакт состояния оператора.

## Что делает оператор (downscale-broker --cloud=X --replicas=0, последний брокер в ДЦ)

`DownscaleKafkaBrokerTask` + `DownscaleMdbReplicasTask` (one-cloud-ops):
1. `resolveBrokerId(host)` — AdminClient describeCluster по хосту
2. `decommissionBrokerById` — alterPartitionReassignments round-robin (без дублей брокера;
   при 1 брокере на ДЦ = автоматически 1 реплика на ДЦ), с валидацией RF
3. цикл `isBrokerDrained` (партиций на брокере нет)
4. `unregisterBroker(brokerId)` — Admin API
5. withdraw service + withdraw storage в облаке (последний брокер = `isWithdrawing: true`)

Застряло на precondition: `isReadyForActions=false` («No one primary» из-за протухшей
модели нод). Дальше сделали руками.

## Лечение (вручную по шагам оператора)

Инструменты: expect+mcc ssh на живой брокер, single-file Java `java -cp "/opt/kafka/libs/*"`
с `/opt/kafka/config/client.properties` (пользователь `super` — хватает на reassignment
и unregister). Скрипты: /tmp/Decommission.java, /tmp/Unregister.java, /tmp/RackCheck.java.

- workspace: оператор успел перелить партиции (0 осталось) → сделали только unregister 20001.
- vahter: decommission не начинался → перелили 129 партиций руками (round-robin по
  pc/rc/ec), дождались drain, проверили `DUP_RACK=0` (одна реплика на ДЦ!), unregister 20001.
- Withdraw в облаке: `mcc stop` service → поллим до FINISHED/STOPPED →
  `mcc withdraw --type service` → `mcc withdraw --type storage "<queue>/broker"`
  (storage non-empty → уравнение через pexpect; см. mcc-host-worker/commands/lifecycle.md).
- После withdraw оператор увидел кластер AVAILABLE (`Is ready for actions: true`), но
  задача workspace зациклилась («Failed to withdraw service ... Could not execute request»
  — сервис уже выведен нами). Лечится `mcc op_stop <partition> kafka.downscale-broker`
  (останавливал пользователь).

## SQL (прод, port-forward 53480)

Операции к моменту лечения уже сами ушли в `failed` (attempts_left=0). Закрыли вручную:

```sql
UPDATE operations SET status='done', in_processing=false, finished_ts=now(), error_message=NULL
WHERE id IN ('4af4a156-b149-4ac5-a456-5e7a530812a1','2ecd2303-e36b-4eff-b70f-85e0ff1f2ce8')
  AND status='failed';
```

## Итог

- Оба кластера: 3 брокера, по одному на ДЦ, DUP_RACK=0, метаданные чистые.
- Операции done. Задачу оператора останавливает пользователь op_stop-ом.
- Корневая причина зависания — баг оператора: модель нод не чистится от удалённых
  контроллеров (ghost `1.controller.*.kc`) → «No one primary» → precondition false навсегда.
