# MDBSUP-4939 — adtech Kafka: delete_hosts (hc) падал, лидер KRaft застрял на выводимом контроллере

Дата: 2026-08-27. Кластеры adtech `ok-events` (12daef01-ca61-4c6b-b586-f46d06c1c329) и
`vk-events` (12d62bd8-c9d3-4b6b-890f-9eadc3805ef2), kafka, production, criticality A.
Перестройка контроллеров hc → ec/kc/pc; удаление hc-контроллера.

## Симптомы

- **ok-events**: операция delete_hosts (hc) `efabd6aa-a5f6-4772-a702-989220b4df36` — FAILED
  ×5 runs (15:20–15:50 UTC), ошибка `Leader node 10001 not found in updated quorum PMS —
  leader migration likely failed` (тип `LEADER_NOT_FOUND_IN_QUORUM`), attempts_left=0.
- **vk-events**: операция delete_hosts (hc) `646abe20-de53-4302-b644-efe307280a76` — первый
  run FAILED (`Config reload failed for hosts: [1.broker...pc...]`, HOST_NOT_READY), retry
  завершил успешно → done (18:43 МСК). hc удалён из облака и host_state.
- Поддержка видела в облаке «только KC-инстансы» — не подтвердилось: все инстансы
  обоих кластеров на месте (шум/устаревшее состояние на момент проверки).

## Корневая причина (ok-events)

Workflow `downscaleKafkaControllerInCluster` (mdb-processing), шаги последнего run:
`cloud_getServiceInfo → cloud_getExistingServiceDcs → cloud_getInfosForServices →
getVariable → removeControllerFromQuorum (COMPLETED) → kafka_host_getLeaderId ×2 → FAIL`.

1. `removeControllerFromQuorum` обновил **только PMS**: `kafka.controller.quorum` =
   `11001@kc,12001@pc,14001@ec` (layout `hc,kc,pc,uc,ec`; node.id = 10000+dcpos*1000+idx,
   hc был dcpos=0 → 10001). Рендер конфигов на хостах — следующие шаги флоу.
2. Фактический KRaft-лидер остался на выводимом hc (`LeaderId: 10001`, все 4 контроллера
   active, voters в конфигах старые — с 10001, кластер здоров, lag 0).
3. `kafka_host_getLeaderId` возвращает 10001 → его нет в новом PMS-кворуме → workflow
   фейлится и **не мигрирует лидера принудительно**. Все 5 retry идентичны: лидер сам
   с hc не уходит, поэтому «рестарт операции не помог» (из тикета поддержки).

## Фикс (ok-events)

1. `mcc sshexec … 1.controller.ok-events-adtech-kafka.hc… "systemctl stop kafka-controller"`
   — контроллер-лидер остановлен (SIGTERM=143), кворум 3/4, majority сохранён.
2. Перевыборы: новый лидер **11001 (kc)**, живые voter'ы 12001/14001 lag 0, мёртвый 10001 —
   единственный «отстающий» follower (норма). Брокеры-обсерверы [21001,22001,24001] lag 0.
3. Retry операции `efabd6aa` через UI mdb-data → флоу прошёл до конца: перерендерил
   `controller.quorum.voters` на контроллерах и брокерах (без 10001), удалил hc-хост
   из облака и host_state. Операция done (23:03 МСК).
4. Верификация: voters везде `11001@kc,12001@pc,14001@ec`; `LeaderId: 12001` (мигрировал
   ещё раз в процессе рестартов — норма); hc-инстансов в облаке нет.

## Остаточные хвосты

- **vk-events: pc- и ec-контроллеры остались со старым конфигом** — в voters прописан
  мёртвый `10001@1.controller.vk-events…hc…:9093` (kc-контроллер и все 3 брокера — уже
  чистые). Рассинхрон voters (см. INCALL-42685 в known_issues) — риска для текущей
  работы нет, но при будущих выборах будет попытка достучаться до мёртвого хоста.
  Дочистка: `confp --oneshot && systemctl restart kafka-controller` на pc и ec по одному.
- ok-events: `describe --status` после починки ещё показывал `CurrentVoters: [10001,…]` —
  список voter'ов в metadata log обновляется записями QuorumLeaderChange; конфиги чистые,
  кворум из 3 voter'ов работает. Наблюдательный нюанс, не блокер.

## Грабли / паттерны

- **Temporal history eventId — строка**, не число: `select(.eventId == 43)` пусто,
  работает `select(.eventId | tostring == "43")`.
- **kafka-metadata-quorum.sh на брокере**: `--command-config /opt/kafka/config/client.properties`
  (НЕ `/etc/kafka/...` — его нет), `--bootstrap-server <FQDN хоста>:9092` (localhost →
  SSL hostname verification failure).
- sshexec с `sudo` на контроллере падал `OCI runtime error` — без sudo команды работают.
- Диагностика кворума: describe с брокера ок; `MaxFollowerLagTimeMs: -1` при одном
  мёртвом voter'е — ожидаемо, смотреть по-узлово `describe --replication`.
- Диагноз «EC/PC инстансы не видны в облаке» от поддержки проверять `mcc instances`
  по каждому ДЦ с `-c` — в этом кейсе оказался ложным.
- Кандидат в разработку (не заводил): флоу downscale-контроллера не переносит лидера
  с выводимой ноды — падает с LEADER_NOT_FOUND_IN_QUORUM и не самовосстанавливается на
  retry; стоит либо ждать/мигрировать лидера внутри флоу, либо формулировать ошибку
  с указанием действия.
