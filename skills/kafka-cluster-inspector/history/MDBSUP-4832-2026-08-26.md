# MDBSUP-4832 — modify_cluster висит в 3 кластерах DataTransfer (modifyKafkaController timeout)

Дата: 2026-08-26. Кластеры Kafka ns infra, очередь `datatransfer.db.production.mdb.prod`:

1. trg-190191-dwh `0fa9d946-16a9-4257-86a0-2e0ebfd9c58b`, операция `3436b817-0d42-405e-8d93-26eea898df91` (упавший контроллер **pc**)
2. target-1-dwh `7b0a370c-17d2-4781-88ba-b47790b11eb3`, операция `b16fecd7-d029-4183-8113-114d2faebb7e` (контроллер **kc**)
3. trg-188703-dwh `af671aa7-cb6e-4eb3-9bec-95bf066b9e7d`, операция `05fa90d1-0f1f-4519-866f-a033f2e9810a` (контроллер **kc**)

## Причина

`upsertSysconfig` из modify_cluster (2026-08-21, dev-баг — уже пофикшен) записал в PMS
(application `mdb`) **пустой `kafka.sysconfig`** для controller-ключей всех трёх кластеров.

Цепочка следствий:
- confp при следующем деплое рендерит пустой `/etc/sysconfig/kafka` (и `.j2` — 0 байт);
- kafka-controller падает по `IllegalArgumentException: Could not find a 'KafkaServer' entry
  in the JAAS configuration` (нет `-Djava.security.auth.login.config` из KAFKA_OPTS);
- облако помечает хост UNAVAILABLE/PREFAIL ("Broker is dead");
- `modifyKafkaController` 4 часа (StartToClose timeout) поллит `cloud_getInfoForInstances`
  (retry maxAttempts=0, ~937 вызовов) → родитель `modifyKafkaCluster` FAILED/TIMED_OUT;
- операции в `operations`: failed, attempts_left=0, in_processing=true → блок «Already has
  unapplied operation».

Живые uc/kc/pc-контроллеры держались только потому, что их sysconfig отрендерился до 21.08
и confp с тех пор не перезапускался.

## Диагностика (ключевые шаги)

- Temporal: цепочка `modifyKafkaCluster` → `modifyKafkaController` (timeout) →
  `updateConfigKafkaController` (10k событий, поллинг `cloud_getInfoForInstances`).
- sshexec на контроллеры: `systemctl is-active kafka-controller` = failed; `/etc/sysconfig/kafka` = 0 байт.
- PMS read (`kafka-config-inspector/bin/pms-read.sh`): `kafka.sysconfig` у controller-ключей пуст,
  у broker-ключей тех же кластеров — полный.
- Куча проверена по `db_cluster_version.draft.cluster_params`: `controllerJvmHeapSizeMb=1024`
  = broker `jvmHeapSizeMb=1024` у всех трёх → broker-шаблон подходит без правок.

## Исправление

1. **PMS-запись** (`update.do`, application `mdb` — его читает confp!): `kafka.sysconfig`
   для трёх controller-ключей = broker-шаблон кластера байт-в-байт (1005 байт, Xms/Xmx 1024m).
   ⚠️ Грабля: первая запись ушла в application `ok-pyvault` (как в примере SKILL.md kafka-config-inspector) —
   confp её НЕ читает (backend `app_name: mdb` в `/etc/confp/confp.yml`). Писать в `mdb`!
   (мусорные ok-pyvault-записи затем очищены пустым значением).
2. **Контроллеры**: `rm -f /etc/sysconfig/kafka{,.j2}; confp --oneshot; systemctl restart kafka-controller`
   → sysconfig 1005 байт, `Kafka Server started`, state RUNNING, availability RESERVED.
   Для trg-190191 pc диск предварительно пересоздавался (stop → delete volumes → start — не помогло,
   т.к. конфиг тянется из PMS; purge all после — «none to purge»). Для остальных двух хостов
   хватило PMS+confp+restart без пересоздания дисков.
3. **Temporal restart**: b16fecd7 — POST `/api/v1/namespaces/default/workflows/{id}` (с input из
   history исходного рана); 05fa90d1 — **Reset** (POST `/workflows/{id}/reset?resetType=FirstWorkflowTask&requestId=<uuid>`
   + body `{"requestId","workflowTaskFinishEventId":<первый WORKFLOW_TASK_COMPLETED eventId>}`) — правильный путь.
   Оба COMPLETED (modify-controller + modify-broker).
4. **Прод-БД**: 3436b817 проставился done сам (callback mdb-processing); b16fecd7/05fa90d1 закрыты руками:
   `UPDATE operations SET status='done', in_processing=false, finished_ts=now(), error_message=NULL WHERE id IN (...) AND status='failed';`

## Грабли сессии

- Запись в PMS: application в `update.do` должно совпадать с `app_name` backend'а confp (`mdb`),
  иначе значение ляжет мимо.
- Temporal UI API: старт workflow — `POST /api/v1/namespaces/{ns}/workflows/{workflowId}`
  (CSRF: cookie `_csrf` + header `X-CSRF-Token`); reset — `/workflows/{id}/reset?resetType=...&requestId=...`
  с `workflowTaskFinishEventId` в body. Endpoint `/workflows/start` игнорирует workflowId из body и
  создаёт workflow с id "start" — не использовать!
- История workflow: `GET /api/v1/namespaces/{ns}/workflows/{wid}/history?runId=<run>` (не `/runs/{run}/history`);
  пагинация — полный nextPageToken (не обрезать!).
- `mcc status`/`instances` по имени сервиса datatransfer-очередей отдаёт EntityNotFoundException —
  обход: `mcc instances "%" -F "String(host).indexOf('<cluster>')>=0"` (+ `-c <dc>`).
- `mcc purge <queue>/<role> all` после пересоздания дисков — освобождает квоты; «none to purge» = чисто.
- tsh port-forward 53480 может рвать соединения при живом LISTEN — рестарт `tsh proxy app ...`.

## Итог

Все три операции modify_cluster выполнены (done), контроллеры в кворумах, PMS восстановлен,
блокировки сняты. Dev-баг upsertSysconfig пустого значения — уже пофикшен командой.
