- **Операция:** modify_cluster `34343bf6-c48b-4b55-9f2b-e2a4c7220fcd` — заглушка, полный разбор в jira-mdbsup-solver: [MDBSUP-5281-2026-09-10.md](../../../jira-mdbsup-solver/history/MDBSUP-5281-2026-09-10.md)

## Специфика Kafka

- Disk 100% от **данных** топика `billing.transaction_groups` (RF=3, все 10 партиций на каждом
  брокере по ~16G). При disk full контейнер kafka-broker падает с `OCI runtime error` и уходит в
  `systemctl failed` — рестарты не помогают, нужен только resize диска или очистка retention.
- Реальный размер NVME volume — 180G при заявленных 190G в операции (declared vs actual расходится).
- Факт-размер проверять `df -h /mnt/data`, состав — `du -xh --max-depth=2 /mnt/data/log | sort -rh | head`.

## Где хранится заявленный диск брокера

- **`db_cluster_version` (последняя строка по `create_ts`), `cluster_params->>'diskGb'` —
  верхнеуровневый ключ jsonb, НЕ внутри `kafkaParams`** (в kafkaParams только controllerDiskGb).
  Упавшая modify-операция успевает записать туда **целевое** значение (250) до старта workflow —
  после этого UI не даёт запустить resize на то же число. Разблокировка: `jsonb_set(cluster_params,'{diskGb}','249')`
  для последней строки (сделано в MDBSUP-5281, чтобы запустить 250).
- В БД mdb нет таблиц/колонок с именем `disk` — поиск только через `cluster_params->'diskGb'`.
- В Temporal пусто по operationId + ошибка «Couldn't find workflow in processing to sync status» =
  workflow не создался на start-фазе; операция остаётся `failed`+`in_processing=true` и блокирует
  новые. Закрытие: `status='canceled', in_processing=false, finished_ts=now()`.
