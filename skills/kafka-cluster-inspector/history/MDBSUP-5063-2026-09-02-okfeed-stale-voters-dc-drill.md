# MDBSUP-5063: okfeed — 18 мин без кворума на учениях ДЦ Пахры (устаревшие voters после downscale контроллеров)

**Дата:** 2026-09-02 (учения 14:12–14:30)
**Кластер:** `okfeed-eventstream-kafka` (eventstream, fc8816aa-2219-4615-87aa-c4233883b7da; 12 брокеров по 4 в ec/kc/pc; контроллеры ec=13001, kc=11001, pc=14001; cruise в dc; namespace infra)
**Тикет:** MDBSUP-5063. Тот же класс корня, что MDBSUP-4970 (stale voters), но другой механизм отказа.

## Инцидент

Учения «отключение Пахры (ec)» 14:12–14:30: клиенты ловили NOT_LEADER_OR_FOLLOWER ~18 мин,
запись не проходила. Восстановилось само при возврате связности (14:29:45.579, epoch 801→802, лидер 14001).

## Корень

Смешанные `controller.quorum.voters` после недоведённого рендера при выводе dc/rc-контроллеров
(31.08, серия из 11 `delete_hosts`, все done):

| Хост | mtime конфига | voters |
|---|---|---|
| controller ec | 27.08 (add_hosts) | 5: dc(10001), kc, rc(12001), ec, pc — stale |
| controller pc | 29.08 | 5: dc, kc, rc, ec, pc — stale |
| controller kc | 31.08 17:27 (delete_hosts) | 3: ec, kc, pc — ок |
| брокеры | 31.08 | 3 — ок |
| PMS `kafka.controller.quorum` | — | 3: ec, kc, pc — ок |

`delete_hosts` перерендерил только kc-контроллер и брокеров; ec/pc-контроллеры не трогались.
Пока живы все 3 — кластер здоров (3 из 5 набирается). При учениях фактический сетевой паттерн:
**kc отрезан от обоих соседей** (в vote-запросах kc оба `UNRECORDED`, ни одного ответа),
а pc↔ec был жив (pc отдавал голоса ec). Пара pc+ec = 2 голоса, но по своим 5-voter конфигам
им нужно 3 → кворума нет весь период → активного контроллера нет → лидерства партиций
не переизбираются. С корректными 3-voter конфигами pc+ec (2 из 3) выбрали бы лидера за секунды.

## Выводы для ответов «достаточно ли N контроллеров»

3 контроллера по 1 на ДЦ переживают потерю одного ДЦ (2 из 3 — большинство). Бот в чате
«насчитал 5 контроллеров» по stale-конфигу ec/pc — реальные узлы сверять с host_state/облаком,
не с конфигом одного хоста.

## Починка (02.09 23:21–23:23)

1. ec (follower): `confp --oneshot` (рендер сразу корректный, vault-pki не споткнулся) →
   `systemctl restart kafka-controller` → вошёл follower с voters=[14001,13001,11001].
   При этом лидерство само переехало pc→kc (epoch 802).
2. pc (уже follower): confp + restart → вошёл follower, лидер прежний kc, без failover.
3. Верификация: брокеры и rscheck@kafka active, ошибок «dead» нет; rscheck-кэш не протух
   (лидер 11001 присутствовал в старых списках тоже).

## Грабли

- Смешанные voter-листы «работают», пока живы все узлы с максимальным списком: деградация
  проявляется только при потере связности — как здесь (нужен 3-й голос из 5, которого нет).
- `delete_hosts` НЕ гарантирует перерендер конфигов на выживших контроллерах — после любого
  изменения кворума сверять `controller.properties` (+mtime) на **всех** контроллерах с PMS.
- Диагностика: `grep 'the leader is'` + `Completed transition to CandidateState(...voteStates=...)`
  по всем контроллерам — сразу видно, кто кому не отвечает (UNRECORDED = нет связности).
- mtime конфига — быстрый маркер: stale-хосты рендерились до операции изменения кворума.
