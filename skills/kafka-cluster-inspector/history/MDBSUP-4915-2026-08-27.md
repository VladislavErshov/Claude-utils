# MDBSUP-4915 — Kafka upmetric-recvw-kafka: downscale-broker завис в финале, op_stop хватило (27.08.2026)

Кластер `upmetric-recvw-kafka` `80d4d384-57d4-44cc-89b9-466acbdfb212` (mail, ns infra, fullQueue
`upmetric-recvw-kafka-mail-kafka.mail.db.production.mdb.prod`). Операция `417f0c53-d37a-47e4-a5c2-011eb5c560b2`
delete_hosts (27.08 12:34 UTC, удаление брокера hc) висела in_progress на `get_kafka_downscale_broker_result`.

## Отличие от [4895](MDBSUP-4895-2026-08-26.md) / [4899](MDBSUP-4899-2026-08-27.md)

Оператор ВСЁ успел сделать (decommission + unregister + withdraw service/storage — инстанса в облаке
нет, в метаданных Kafka 3 брокера kc=21001/pc=22001/ec=23001), но финальный `KafkaAdminAction` на
ec-брокере завис (invoked 15:02:50, оператор в `waiting for action completion`, state не дошёл до
serviceWithdrawn/storageWithdrawn=true). Операция in_progress с ЖИВЫМ ретраем таски
(`need_retry`, delay_after_sec=60, attempts_left восстанавливается) → блокирует новые операции.

`isWithdrawing: true` в state задачи — НЕ «withdraw начался», а флаг «последний брокер в ДЦ»
(ставится в `checkAndFillArguments()` при currentReplicas==1, DownscaleMdbReplicasTask.java:237).

## Лечение

1. Убедиться, что оператор ничего не должен доделать: api-versions (hc нет в метаданных),
   `mcc instances`/sshexec на hc-хост (EntityNotFoundException = инстанс выведен), host_state чист.
2. `mcc --local -n infra -c hc op_stop "queue://<fullQueue>" kafka.downscale-broker`.
3. Ждать ~2 мин: таска при очередном 60-сек ретрае видит TASK_ABSENT → done; планировщик сам
   прогоняет `update_db_connection_url` + `finish_task` → операция закрывается **штатно, без SQL**.
   (17:54:46 таска done → 17:55:59 операция done.)

## Итог

Кластер 3 брокера (kc/pc/ec) + 3 контроллера + cruise(kc), KRaft-лидер kc, alerts оператора чистые.
Паттерн: если операция in_progress с живым коротким ретраем таски и оператор всё сделал — достаточно
op_stop, SQL-правка не нужна.
