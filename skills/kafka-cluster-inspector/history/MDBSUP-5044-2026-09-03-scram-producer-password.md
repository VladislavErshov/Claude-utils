# MDBSUP-5044 (2026-09-03) — перегенерация SCRAM-пароля update_user'ом уронила продьюсер

## Симптом

- Продьюсер oneme-databus (клиент UCP_ASYNC_MDB) не пишет в `oneme_ucp_and_analytics_views`
  кластера extdbpu (94bed650-7adf-4b78-9640-37a311033e65): `Failed to update metadata after 10000 ms`,
  `ack=0` и telnet 9092 не помогают (telnet — TCP, SASL им не проверяется).
- Серверная сторона «чистая»: топик 96 партиций, все лидеры на месте, ISR=3, ACL есть,
  `denied` в логах нет — потому что это НЕ авторизация (ACL), а **аутентификация** (SASL).
- В брокерных логах — непрерывный поток `Failed authentication ... invalid credentials with
  SASL mechanism SCRAM-SHA-256` от 8 IP продьюсера (4 пода dual-stack: 10.177.135.43/.49,
  10.206.185.224/.225 + IPv6 fd00:b4c4:c114:...:37f0/37f1, fd00:b4c0:7c0:...:1ce9/1cea),
  ~7k фейлов/час на брокер, **на всех брокерах всех ДЦ**.

## Корень

mdb-операция `update_user` **перегенерирует SCRAM-пароль**, даже если в запросе `"password": ""`
(в operation_model операции пароль всегда пустой). a.perevalov обновлял ACL через mdb-data UI →
пароль менялся молча → клиент с зашитым старым паролем ломается.

## Почему «Failed to update metadata»

Без успешного SASL-хендшейка клиент не получает метадату вообще → producer упирается в
max.block.ms с общим сообщением «Failed to update metadata after 10000 ms», без упоминания auth.
Несоответствие кред = именно этот симптом, «ошибки по правам» клиент не покажет.

## Фикс

На стороне заявителя: взять актуальный пароль `ucp_content_event_producer` (mdb-data UI →
пользователи → показать пароль; vault: `zkv/mdb/oneme/kafka/extdbpu-oneme-kafka.oneme.db.production.mdb.prod/users/ucp_content_event_producer`)
→ обновить конфиг клиента UCP_ASYNC_MDB в PMS ns=oneme (app=oneme-databus) → перезапустить продьюсер.
Со стороны MDB правок не нужно. НЕ «чинить» повторным update_user — пароль снова перегенерится.

## Грабли

- **update_user в mdb всегда перегенерирует пароль** — любые ACL-правки юзера через mdb-data UI
  ломают всех его клиентов при следующем реконнекте (не сразу! — сессии живут). Предупреждать
  заявителей: после изменения ACL юзера — сразу синхронизировать пароль его клиентам.
- SASL-сессии переживают смену кред на сервере: разрыв между операцией и падением клиентов
  может быть часы/дни — не ищи событие ровно в момент начала фейлов.
- Фейлы аутентификации пишутся на INFO Selector'ом на каждом брокере: grep
  `Failed authentication` по брокерам всех ДЦ — если одни и те же IP фейлятся кластерно,
  это креды клиента, не брокер.
- Имя фейлящегося SASL-пользователя в INFO-лог не пишется — ищется по ACL топика
  (кто writer/reader) + IP клиентов.
- Динамик фейлов по часам (uniq по `^\[2026-08-26 16`) позволяет найти точную минуту
  начала/конца инцидента и сопоставить с operations прод-БД (схема: users.updated_ts ↔
  operations типа update_user; users.vault_path — путь к актуальному паролю).
- Смежное (не причина тикета): фантомный hc-voter в KRaft кворуме — починен раньше в тот же
  день, разбор — [MDBSUP-5044-2026-09-03-quorum-phantom-hc-voter.md](MDBSUP-5044-2026-09-03-quorum-phantom-hc-voter.md).
