# MDBSUP-5082 — 100% CPU на slave-хостах ZC (donut-goals, donut-onetime): error storm rsyslogd (2026-09-03)

Тикет: «несколько дней 100% CPU на slave-хостах shard1 ZC, остальные хосты 4–5%, нагрузки нет».

## Кластеры
- `donut-goals` `7893e706-0f14-43bc-9c27-34b1df88591f` — `1.shard1-db.donut-goals-mdb7630-redis.zc.one-infra.ru`
- `donut-onetime` `0ffef58a-86f9-411b-82ca-f28667a4afaa` — `1.shard1-db.donut-onetime-mdb7630-redis.zc.one-infra.ru`

Оба — на **одной физической ноде `srvz2249`** (общий volume `/dev/mapper/srvz2249-one` смонтирован в `/one/logs`) — поэтому затронуты одновременно и только ZC-хосты этих кластеров.

## Цепочка
1. **29.08 12:17** rsyslogd ловит ENOSPC при записи в `/one/logs/systemd.log` (что переполнило том ноды — не выяснено, вне тикета).
2. rsyslogd на каждую ошибку записи пишет сообщение → destination `/var/log/syslog` (rsyslog.conf `$template DynProgramLog` для /one/logs + стандартный rootfs /var/log).
3. `/var/log/syslog` раздулся до 5,3 ГБ и заполнил overlay `/` (всего 10G) до 100% → теперь падает и она → новая ошибка → **самоподдерживающийся error storm**. rsyslogd ~90% CPU + journald ~60% = 100% CPU контейнера с 29.08 (TIME+ rsyslogd 4,5 суток).
4. **redis-server не при чём**: 0,4–0,5% CPU, slave, `master_link_status:up` в течение всего шторма. Ротация `/one/logs/rsyslogd.log` (~ежечасно, по ~50 МБ gz, файл 6,9 ГБ) не давала тому тому кончиться — поэтому шторм не самоостановился.

## Диагностика (быстрый путь)
- `top -bn1` → не redis, а rsyslogd/journald (в рединсе-инцидентах **всегда сначала** смотреть процесс, а не предположения про данные).
- `journalctl -n 12` → тысячи `rsyslogd: file '/var/log/syslog' write error ... No space left on device` каждую секунду.
- `df -h` → `/` 100%; `ls -la /var/log/syslog` → 5,3 ГБ.
- Хвост `/var/log/syslog` указывает на первый источник: `file '/one/logs/systemd.log'[9] write error ... ENOSPC` от 29.08.

## Фикс (03.09, на обоих хостах)
```bash
truncate -s 0 /var/log/syslog   # не rm — fd у rsyslogd должен остаться валидным
systemctl restart rsyslog       # сброс зависшего omfile-состояния; redis не трогаем
```
Результат: `/` 1–2% used, rsyslogd/journald 0% CPU, `cluster_state:ok`, 16384/16384 слотов.

⚠️ Грабля: сразу после truncate+restart `df` может показывать занятость (6,1 ГБ при `du` 1,1 ГБ) — место держит fd старого rsyslogd, освобождается после его смерти; проверять повторно через минуту.

## Остатки (на команду образа/инфры, вне тикета)
1. rsyslogd **не rate-limit'ит собственные сообщения об ошибках записи** → error storm роняет CPU контейнера. Нужен лимит (`$imjournalRatelimit`/`errorfile` + подавление повторов) в образе.
2. `logrotate` `/var/log/syslog` не отрабатывал с 23.08 (weekly; compress невозможен на 100%-диске — тупик).
3. Выяснить, что переполнило том `/one/logs` ноды srvz2249 29.08 (на томе `prjquota` — возможен пер-контейнерный лимит).
4. Тонкие rootfs (10G overlay): 5 ГБ логов его забивают мгновенно.
