# MDBSUP-4910 — Redis as-repuser: два мастера в шардах 2/4/9/16, заблокированные операции (2026-08-27)

Реальный экземпляр типового кейса «В шарде 2 мастера» (см. [../SKILL.md](../SKILL.md) →
«Runbook для дежурного» и вики «Дежурство MDB: Redis»); отличается причиной
(не зачистка диска, а непрошедший replicate после add_hosts) и багом failover-вейтера.

## Кластер
- `as-repuser` (Redis Cluster, 20 шардов × 4 реплики ec/kc/pc/rc), cluster_id `677793b4-6f2d-437a-8958-19adfc32d8e6`, ns infra, mdb4831.

## Что было
- `add_hosts` (cec1f26c, 12:42–12:46) добавил 4-ю реплику (ec) в каждый шард — done.
- `change_primary` (c74fd683, failoverRedisCluster) — 3 run'а упали (13:05/13:15/13:31 MSK), затем ретрай пользователя (15:49) — тоже FAILED.
- Ошибка: «Host fd00:b4c4:c110:101:1:0:323f:0 is still Redis master after failover» (run 3), «…fd00:b4c0:2c0:1:1:0:d19:0…» (run 4 = shard1-ec).
- В шардах 2/4/9/16 по 2 мастера: **ec-нода — мастер без слотов** (при add_hosts `CLUSTER REPLICATE` не отработал), слоты у старого мастера (kc/kc/kc/pc), pc+rc — его реплики. 24 мастера на 20 шардов.
- kc16 дополнительно висел как `master,fail` в gossip-виде ec16; фактически redis жив (minion на хосте не запущен — отдельная проблема хоста), репликация pc16/rc16 с ним шла.

## Диагностика
- operation_model.change_primary: 14 хостов = **hostsToPromote** (кого ПРОМОУТНить), `maxShardsToProcess: 9`, force=false, takeover=false.
- Workflow `FailoverRedisClusterWorkflowImpl.failoverAndWait(host)`: getMasterHostFromSingleHost → `clusterFailover` на самом host → `RedisFailoverWaiter.waitUntilHostIsNotMaster(currentMasterHost)`.
- **Баг**: если целевой хост УЖЕ мастер, то currentMasterHost == сам хост; `CLUSTER FAILOVER` на мастере даёт «ERR You should send CLUSTER FAILOVER to a replica», activity её глотает («already a master»), после чего waiter ждёт, пока цель перестанет быть мастером → таймаут → «still Redis master after failover». Ретраи операции бесполезны.
- ACL-подключение к нодам — [../SKILL.md](../SKILL.md) → «Подключение» (юзер `master`,
  пароль masterauth).

## Фикс топологии (кластер)
- Связность ec16→kc16 проверена (PONG 6379), fail-флаг — stale gossip.
- На пустых мастер-нодах выполнен `CLUSTER REPLICATE <id настоящего мастера>`:
  - ec2 → 9951780f… (kc2), ec4 → 92744bbb… (kc4), ec9 → c7cc7624… (pc9), ec16 → c6b163b0… (kc16).
- Итог: 20 мастеров, по 1 на шард, `master_link_status:up`, `cluster_state` ок.
- Все 14 hostsToPromote в итоге уже мастера (7 промоутнул run 2 в 13:15 MSK, остальные были мастерами и так) — цель операции достигнута без изменений.

## Остатки / риски
- **Баг в mdb-processing** (стоит завести тикет): `FailoverRedisClusterWorkflowImpl` + `RedisShardActivityImpl.clusterFailover` — идемпотентность при «цель уже мастер» сломана (swallow ошибки → wait до таймаута).
- Minion на kc16 не запущен (`ServiceValidationException: Minion … is not running`) — хост неуправляем через mcc, redis жив. Проверить/перезапустить миньон.
- Temporal API: история только последнего run'а; failure-событие может быть на 2-й странице (nextPageToken) — смотреть обе.
