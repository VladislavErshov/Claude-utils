# MDBSUP-5046 (2026-09-01): ok-cache — окно таймаутов при изоляции Пахры: мастера 3 шардов были в kc/hc

**Кластер:** `ok-cache` `8fa412d8-e377-4ed2-a56b-6ce521829c1e`, проект recommender, шардированный Redis, **8 шардов × hc/kc/pc** (24 хоста, `1.shard${i}-db.ok-cache-recommender-redis.<dc>.one-infra.ru`), criticality A.
**Тикет:** MDBSUP-5046 (Аскаров Эмиль, 02.09). Заглушка — jira-mdbsup-solver/history.
**Клиент:** ok-friends-mediator, command timeout 35 ms.

## Вопрос тикета

При учениях «отключение Пахры (kc, hc)» 01.09 ~12:15 у сервиса подскочили тайминги GET до 35–40 ms. Заказчик считал, что «перевели >2/3 мастеров в pc, кворум сохранится», и спрашивал, почему GET просели, «ведь клиент может читать с реплик».

## Раскладка мастеров на момент резки (восстановлена по логам всех 8 pc-хостов)

|---|---|---|
| 1, 3, 4, 5, 6 | **pc** | 5 мастеров, кворум был |
| **2, 7, 8** | **kc/hc** | отрезаны вместе с Пахрой |

change_primary от заказчика: 26.08 (shard1→pc, shard4→kc, shard5→kc) и 31.08 19:17 (shard3,4,5→pc). Замысел «большинство в pc» достигнут (5 из 8), но 3 мастера физически остались в изолируемом ДЦ.

## Хронология (логи `/mnt/logs/dbms/redis.log`, pc-хосты)

- ~12:13:55 — резка ACL; 16 из 24 нод ушли из видимости pc.
- 12:13:58–12:14:25 — волны `FAIL message received` (cluster-node-timeout = 10000 ms, из modify-параметров кластера).
- ~12:14:00 — **первые кампании реплик провалились**: мастера ещё не признали FAIL консенсусом (голосов < большинства).
- 12:14:04.496 — shard8-pc выиграла выборы (ep73); 12:14:20.401 — shard2-pc (ep74, «Start of election delayed (rank #0)» была в 12:13:59); 12:14:40.882 — shard7-pc (ep75, со второй попытки).
- **Окно недоступности слотов: шард 8 ~10 c, шард 2 ~25 c, шард 7 ~45 c.**
- 12:30:38–45 — связность вернулась: 16 нод `Clear FAIL`; 5 вернулись как «master without slots» (бывшие мастера шардов 2/7/8 + 2 зомби без слотов), демотировались, пошли ресинки. Повторные мелкие FAIL-флапы 12:33 и 12:35.

## Ответ на вопрос «почему GET, ведь можно читать с реплик»

1. Полка 35–40 ms на графике = **стена клиентских таймаутов**: запросы в слоты отрезанных шардов жили ровно до 35 ms и ретраились, пока шли обнаружение отказа и выборы (по определению > cluster-node-timeout 10 c).
2. Читать неоткуда: живая реплика отрезанного мастера одна и она же кандидат на выборы; **до выигрыша выборов клиент не роутит на неё запросы** — карта слотов указывает на старого мастера. read-from-replica в Redis Cluster требует свежей топологии, а после каждого фейловера идёт MOVED + refresh карты — хвост latency по всем шардам.
3. Кворум-математика сработала штатно; проблема не в кворуме, а в том, что 3 мастера находились в изолируемом ДЦ.

## Хвост 1: modify_cluster 01.09 15:53 — failed + застрял in_processing (закрыт 17.09)

`modify_cluster` `bead2d9e-6550-4dc2-8520-9c9910fa0baf` (maxim.maltsev; replBacklogSize 1gb, ioThreads 4, replTimeout 500, clusterNodeTimeout 10000):
- Упали **все 8** child `updateRedisConfig` (не только shard2 из error_message — parent сообщает первый фейл; имена workflowId = `<opId>_update-config_shardN`).
- Причина: **вторая итерация учений** — Пахру дёргали циклически 15:37–15:58 (FAIL/Clear-флапы в логах redis); SSH/обновление конфига до хостов висело, activity `update` с StartToClose **30s** × maximumAttempts 3 → RETRY_STATE_MAXIMUM_ATTEMPTS_REACHED. Два рана (15:53 и 16:05 МСК) — оба в окно флапов.
- Конфиг **не применился нигде** (проверено config get на всех 8: io-threads=1, repl-backlog=128M).
- Операция осталась `failed` + `in_processing=true` + attempts_left=0 → блокировала новые операции кластера с 01.09. 17.09 закрыто DML: `UPDATE operations SET in_processing=false, finished_ts=now() WHERE id='...' AND status='failed'` (status='failed' сохранён честным). Modify можно перезапускать в спокойное окно.

## Хвост 2: shard6 — ручной repl-backlog-size с опечаткой

- shard6-pc: redis.conf `repl-backlog-size 1028mb` (опечатка, похоже на 1024mb) → runtime 1342177280 (~1.25G); на остальных шардах 128M. Вероятно, ручной фикс «вечной переливки» по ранбуку — не зафиксирован через UI/PMS как единый параметр кластера. Перезапуск modify (replBacklogSize 1gb на все шарды) унифицирует и это.

## Выводы для следующих учений

- Перед изоляцией ДЦ **все мастера выводить в живые ДЦ** (сейчас после фейловеров все 8 в pc — при следующей резке Пахры переключений не будет вообще; потеряются только реплики).
- Кворум 5 из 8 достаточен для выборов; узкое место — cluster-node-timeout 10s + каскад (PFAIL→FAIL-консенсус→выборы), окно 10–45 c при таймауте клиента 35 ms. Если заказчику нужно меньшее окно — снижать cluster-node-timeout (сейчас 10s, менять осознанно) или на время учений поднимать клиентский timeout.
- modify/config-update операции **не запускать в окна учений**: activity StartToClose 30s не переживает даже краткий флап связности, а фейл оставляет операцию в in_processing.
- Диагностика раскладки «кто мастер» постфактум: логи pc-хостов (`Failover election won`), ipv6→шард маппится последовательно (shardN-pc = fd00:...:119e+(N-1)); `cluster myid` в выводе sshexec маскируется секрет-сканером — не полагаться на ID, мапить по себе/myself-адресам.
