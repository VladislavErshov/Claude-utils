# MDBSUP-5322 — as-mrasreduser: ресайз PT60H-таймаут, pc_1 STOPPED (shard35) и CORRUPT-диск (shard56) (2026-09-10)

Тикет: «операция modify_cluster (ресайз, preset 15) упала с Timed out after PT60H, кластер general_issue ("один из шардов недоступен"), блокирует миграцию из Пахры».

Кластер: `as-mrasreduser` `e99fa706-c41c-4529-86cd-92da2eeead47`, mdb4831, Redis 8.0, шардированный, 56 шардов × 3 реплики (pc/kc/rc) = 168 хостов, criticality A.
Операция: `5c0425bb-967d-4fe2-8bce-7239b03a071b` от 09-01 16:41 МСК.

## Топология (важно для диагностик этого кластера)

Мастера шардов живут в **сервисной сети 10.11.35.x, multi-instance** (десятки redis-процессов на IP, порты 6379–6434). Все 168 one-infra-хостов (pc/kc/rc) — **slave'ы** этих мастеров. Не пугаться, что `cluster nodes` с one-infra-хоста показывает «мастера» на посторонних IP — это обслуживающий слой, миграция из Пахры = переезд мастеров на our-хосты.

## Цепочка падения

1. **Run 1** (09-01 13:41 UTC): родитель и все дети упали за секунды (причину не копали — автотория), авторетрай через ~20 мин.
2. **Run 2** (14:02 UTC): 54 шарда ресайзились до ~18:45 UTC успешно. Двое не доехали:
   - **shard35 pc_1**: workflow упал `Instance 1.shard35-db...pc.one-infra.ru did not start after resize stop (state=STOPPING, progress=null)`. В облаке инстанс `state=FINISHED, outcome=STOPPED` — остановлен и не поднят; данные целы.
   - **shard56 pc_1**: оба volume (data `cdff7e11-...`, logs `cdff7e10-...`) `state=CORRUPT` на минионе **srvm2285** — физический девайс `/dev/nvme1n1` исчез (`NoSuchFileException`), от того же девайса пострадал и чужой тенант (`chepusher-vkcm-redis .../shard-70-db`). Инстанс застрял `state=NEW` без IP с 09-01, child-workflow позже прибит `TERMINATED by parent close policy` (identity=history-service).
3. `_resize` ждал детишек до `Timed out after PT60H` (09-03 02:02 UTC) → родитель FAILED → операция failed, `in_processing=true` → кластер general_issue, «Already has unapplied operation», миграция из Пахры заблокирована.

## Диагностика (быстрый путь)

- Статусы детей из listing: у 54 шардов последние runs COMPLETED; по `_resize_shard35`/`_resize_shard56` — FAILED/TERMINATED, и у обоих **нет `_rc_1`-воркфлоу вообще** → шарды-виновники находятся за минуту.
- Облако: `mcc instances "%as-mrasreduser%"` по каждому ДЦ → сверка RUNNING по всем 168; дельта = битые хосты (тут: pc 54/56).
- `tool_status --type storage "<queue>/<shard>-db"` → state CORRUPT + причина (девайс/минион) в `details`.

## Фикс (09-10)

1. **shard35 pc_1** (данные целы): `mcc --local -n infra -c pc start "shard35-db.as-mrasreduser-mdb4831-redis"` → RUNNING за ~1,5 мин. Инстанс сам взял роль slave мастера 10.11.35.131 и полным sync'ом догнал.
   - ⚠️ Во время LOADING `info replication` показывал `role:master`, а `cluster nodes` падал с exit 1 — **не паниковать и не лечить до конца загрузки**; после LOADING роль стала slave. Проверять роль только после `loading:0`.
2. **shard56 pc_1** (диск CORRUPT, не мастер — проверено по cluster nodes): delete volumes по UUID (`cdff7e11…,cdff7e10…`, уравнение через pexpect) → `mcc start` → облако выделило новые диски на **живом минионе srvm4347**, инстанс RUNNING через ~3 мин → slave мастера 10.11.35.130:6432, `master_link_status:up`. Старый IP (10.201.73.26) сохранился.
3. `purge "<queue>/shard56-db" all` → «none to purge» (квоты чистые).
4. Пресеты: demand shard34 (эталон OK) = shard35 = shard56 (vCPU=2, MEM=12G, NVMe=41G) — ресайз применён ко всем.

## Реактизация операции (главный сюрприз)

Через ~3 мин после того, как оба хоста стали здоровы (17:33), **reconcile/авторетрай сам поднял новый run** операции (17:36): 54 ребёнка отсеклись `START_CHILD_WORKFLOW_EXECUTION_FAILED_CAUSE_WORKFLOW_ALREADY_EXISTS`, а ровно shard35+shard56 перезапустились и завершились; родитель COMPLETED в 17:56:51, операция в БД `done`, `finished_ts` проставлен, error очищен. **DML в operations не понадобился** (подготовленный UPDATE вернул 0 — статус уже был не failed).

⚠️ Поэтому для таких кейсов порядок такой: починить хосты → **подождать 10–30 мин** (reconcile сам дожимает операцию) → и только потом смотреть на DML. Сверять статус операции в БД непосредственно перед UPDATE (у нас он изменился с `failed` на `in_progress` за час).

## Грабли

- `in_processing=true` у давних `done`-операций этого кластера (create_user, update_user) — **артефакт, не блокер**; блокировку определяет status. Не считать такие строки «зависшими».
- sshexec бывает `Minion ... is not running` / пустой вывод при живом инстансе — минион-пул флапает; проверить `instances "%" -F "...minion..."` и повторить.
- Temporal UI API: пагинация истории может застревать (nextPageToken отдаёт ту же страницу) — надёжнее python-цикл с urllib; `runId` игнорируется (только последний run).
- В cluster nodes записи старых (удалённых) инстансов висят как `slave,fail` со старыми IP — это стейл, не дефект.
