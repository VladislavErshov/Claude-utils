# MDBSUP-5349 — streams-p-vkdating-redis: «100% CPU из-за непрерывного AOF rewrite» на ZC-реплике = на самом деле rsyslogd-цикл при забитом rootfs (2026-09-17)

Тикет: «на реплике shard9 ZC стабильно 100% CPU, AOF rewrite запускается непрерывно; на IC/NC того же шарда такого нет; проверить физхост srvz1175 и почему интенсивность записи аномально высока».

Кластер: `streams-p-vkdating-redis` `ab3f30f8-590b-445e-9373-38de5742d2eb`, шардированный Redis, 9 шардов × 3 ДЦ (ic/nc/zc). Хост: `1.shard9-db.streams-p-vkdating-redis.zc.one-infra.ru` (srvz1175).

## Главное: AOF — ложный след

- Rewrite'ы идут на **всех трёх нодах шарда** синхронно: счётчики `aof_rewrites` 249/250/251, каждые ~5 часов, сам rewrite ~10 сек (`aof_last_rewrite_time_sec`). Это нормальный цикл: датасет ~2.3 GB при maxmemory 6.7 GB, `auto-aof-rewrite-percentage=100` от base ~1.25–1.9 GB → порог достигается за ~5 ч. Нагрузка на реплике ~240 ops/sec (мастер shard9 в IC — ~7300 ops/sec).
- Redis на ZC при проверке ел 0–10% CPU. «Постоянный 100% CPU» давали не он.

## Реальная причина

1. 06-09 04:30 — диск был полон: rsyslogd не смог писать `/one/logs/rsyslogd.log` («No space left on device»).
2. rsyslogd завис в **ошибочном цикле**: ту же ошибку он пишет в `/var/log/syslog` миллионы раз → файл вырос до **10 GB** и забил overlay-**rootfs 10G/10G (100%)** → цикл «диск полон → пишем об этом в syslog → диск ещё полнее».
3. rsyslogd (~14% CPU lifetime avg) + journald (~7%) в этом цикле и давали аномальный CPU инстанса в мониторинге.
4. Соседние IC/NC здоровы (syslog 20M) — проблема локальная на ZC. `/one/logs` к моменту разбора уже имел 202G свободно (первопричина ушла сама), но цикл продолжался.

## Диагностика (быстрый путь)

```bash
# 1) исключить redis: кто реально ест CPU
ps aux --sort=-%cpu | head          # rsyslogd/journald сверху → подозрение на syslog-цикл
top -bn1 -p $(pidof redis-server)   # текущий CPU redis
# 2) syslog и rootfs
ls -lh /var/log/syslog*; df -h /
tail -5 /var/log/syslog             # «write error ... No space left on device» в цикле = диагноз
# 3) сравнить с соседями шарда: aof_rewrites / ops / role — если совпадают, AOF не виноват
```

Отличие от вики-кейса «Забитый rootfs, троттлинг cpu»: там просто растёт syslog; здесь видна конкретная петля «ошибка записи → лог ошибки об ошибке записи».

## Фикс (09-17, одобрен пользователем)

```bash
rm -f /var/log/syslog*        # освободить 10 GB, rootfs 100% → 1%
systemctl restart rsyslog     # сбросить состояние цикла
```

Верификация через ~1 мин: rootfs 128K (1%), syslog 7.6 KB с обычными записями, rsyslogd 0% CPU, `aof_last_write_status:ok`, rewrite'ы в обычном ритме. Пара «No space left» в свежем syslog — доигрывающие записи journald, не цикл. Рестарт redis не нужен (данные на отдельном `/mnt/redis`).

## Грабли

- Мониторинг «CPU инстанса 100%» — это весь контейнер (rsyslogd+journald+vector+exporter), не только redis. Первым делом смотреть `ps aux --sort=-%cpu` внутри хоста.
- mtime у `/var/log/syslog` обновляется даже когда запись фактически не проходит (rootfs полон) — по mtime не судить об объёме записи.
- Ошибка в тикете «AOF снова вырастает на 100% и следует новый rewrite» — визуально похоже на график AOF size с пилой rewrite'ов, но пила одинаковая на всех нодах шарда. Сверять счётчики `aof_rewrites` между репликами шарда — расхождение сразу покажет аномальную ноду.
