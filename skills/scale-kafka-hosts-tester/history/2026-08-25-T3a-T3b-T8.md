## T8 — PASS c находкой бага окружения, не кода

- Рестарт с ИЗМЕНЁННОЙ целью `{hc:2, kc:2}` (`t8-restart-new-goal`):
  - dc-child упал `DOWNSCALE_NOT_ALLOWED` (в облаке dc=2 после T3b, цель dc=1) — guard корректен в многоДЦ-сценарии;
  - hc-child доведён до 2 (COMPLETED);
  - kc-child: rescale 1→2 прошёл, но `waitServiceRunning` таймаут ~8мин → `Service ... is not running yet`.
- **Разбор kc-падения**: хост 2.controller.kc задеплоился, но kafka-controller в crash-loop:
  `node id 12002 must be included in the set of voters ... HashSet(11002,10001,12001,11001,10002)`.
  Конфиг отрендерился без 12002, хотя upsertControllerQuorum ЗАПИСАЛ 6-voter кворум (проверено
  по activity result в history). Причина: деплой и рендер конфига произошли ДО/в момент записи PMS
  (гонка deploy vs PMS-propagation) — вероятно побочный эффект прямой последовательности T3b→T8
  (у one-cloud не было времени применить PMS до старта нового инстанса).
- **Лечение**: direct-start `t8-fix-reload-kc` с целью, равной факту `{dc:2,hc:2,kc:2}` →
  все child skip, reload перерендерил конфиги → workflow COMPLETED, host_state=6.
  (verификация сервиса на 2.controller.kc прервалась mcc TLS-timeout — перепроверить.)
- ⚠️ Урок для прода: если операция упала после rescale, но до reload, новый контроллер может
  стартовать со старым кворумом и уйти в crash-loop. Ретрай операции чинит (reload). Возможная
  improvement: child должен ждать применения PMS перед waitServiceRunning (или рендер конфига
  должен включать самого себя по build-hosts, а не по текущему PMS).

## Решение по багу 1 (crash-loop при гонке PMS→рендер) — БЕЗ изменения кода

- В успешном флоу reload-фаза parent'а перерендерит конфиг — самолечение встроено.
- Если операция упала до reload — её перезапуск скипает деплой и выполняет reload
  (подтверждено t8-fix-reload-kc) — продовый паттерн FAILED→COMPLETED.

  и так сходится ретраем. Наблюдаем на проде; если окно станет проблемой —
  вариант D (instance-pms при бутстрапе) как правильное долгосрочное решение.
