# Скилл /mdb-gitlab-reviewer — ревью MR в mdb-репозиториях

Ревью merge request'ов в GitLab (`gitlab.corp.mail.ru`), прежде всего `mdb/mdb-data`, `mdb/mdb-processing`. Фокус: архитектурные запахи, костыли (особенно в AI-сгенерированном коде и коде от джунов), транзакционность, качество тестов.

## Workflow

1. **Метаданные MR:** `get_merge_request(project_id, merge_request_iid)` — описание, автор, статус, апрувы. Описание часто AI-генерированное — не доверять, сверять с кодом (см. чек-лист п.8).
2. **Диф:** `get_branch_diff(project_id, from: "master", to: <source_branch>)` — список файлов и объём изменений.
3. **Дискуссии:** `get_merge_request_discussions` — почти всегда там уже отревьюил бот Gena (@svc-gena), часто в несколько волн. Читать его findings И ответы автора: авторские оправдания раскрывают намерения и принятые компромиссы. Учитывать вердикты @vl.ershov (апрувер) — они канон (см. «Калибровка»).
4. **Финальный код:** читать файлы через `get_repository_file_raw` с ref = source-ветке. Промежуточные версии не важны — оценивать только итог (MR эволюционирует после ревью, описание может остаться от первой версии).
5. **Вердикт:** структурированный разбор — что костыльно, что нормально, что сделано хорошо. Отдельно помечать «осознанный компромисс, зафиксированный в дискуссиях» vs «реальный техдолг, которому нужен follow-up».

## Чек-лист (стандартный набор, калибруется по новым MR)

### 1. Guard-костыли «зеркало драйвера»
Валидация, воспроизводящая внутренности чужой библиотеки, вместо фикса причины.
- Пример (MR !498, `AbstractUserService.isInvalidVaultPath`): `new URI("https://vault.invalid/" + path)` чтобы «предсказать», упадёт ли vault-клиент (jopenlibs) на пути. Хрупко: библиотека поменяет построение URI — guard тихо разойдётся. Magic-host в продовом коде.
- Правильный фикс — валидация входа на границе API (sync-endpoint не проходит UI-валидацию!) или URL-encoding в месте построения пути.
- **Куда смотреть в первую очередь:** правильное место для такой проверки — vault-клиент в **proxylib** (локально `~/Documents/Git/mdb-commons-lib/proxylib`, для vault-путей — `vault/utils/VaultPathUtils.java`). На момент MR !498 валидации там НЕТ: только `normalizePath` (срезает префикс `zkv/data|show|metadata`). URI-guard из mdb-data — кандидат на перенос в `VaultPathUtils.isAddressable(path)`.
- Валидатор должен жить там же, где конструируется путь (`VaultUtil` в mdb-data / `VaultPathUtils` в proxylib), а не приватным статиком в потребителе; проверять симметрию create/delete-путей.
- **Клиент proxylib строг к ошибкам:** `VaultClientImpl.checkResponseSuccessful` бросает `MdbVaultClientException` на ЛЮБОЙ non-2xx — включая 404 при удалении отсутствующего секрета. При ревью delete-флоу всегда спрашивать: что вернёт Vault, если секрета нет? Если 404 → исключение → crash-loop для юзеров без секрета (это и был исходный баг MDBDEV-3400, «missing vault secret»).

### 2. Утечка специфики одного DbType в абстрактный базовый класс
`dbType == DbType.KAFKA` внутри `AbstractUserService` (общий для Kafka/PostgreSQL/Redis/ClickHouse) — условное поведение в generic-контракте. Чище: overridable hook (`canDeleteSecretAt(path)` и т.п.) или перенос в конкретный `KafkaUserService`. Флагать как архитектурный запах, даже если условие уже сужено после ревью.

### 3. Транзакционность и внешние вызовы
- Метод с несколькими записями (user row + permissions) без `@Transactional` → partial commit при сбое второго шага. Проверять, что у парных save/delete-методов аннотации симметричны.
- Remote HTTP-вызов (Vault, processing) внутри `@Transactional` — долгая транзакция, давление на пул. Мягкий запах, если паттерн до-MR уже был — не блокировать.
- `@Transactional` на оркестраторе батча — анти-паттерн; изоляция по-элементно (свой tx на элемент) + агрегированный отчёт — правильно.
- Проверять: внешний вызов до или после записи в БД внутри tx; что при сбое после внешнего вызова состояние консистентно (idempotent retry?).

### 4. Обработка ошибок: swallow vs strict
- Catch-all, превращающий transient-ошибку (5xx, permission denied) в «безопасный» случай → рассинхрон состояния. Строгая модель (ошибка → rollback → retry) предпочтительнее; исключение — только структурно невосстановимые случаи (неадресуемый путь), и они должны быть узко определены.
- Вопрос про отсутствие сущности: идемпотентен ли delete при 404? Если клиент бросает на missing — crash-loop вернётся для другого подмножества объектов. Всегда спрашивать/проверять поведение клиента на 404, а не только на «кривой» ввод.
- Доменные исключения вместо `IllegalStateException` для I/O-сбоев.

### 5. Батч-обработка и error isolation
Пер-элементный try/catch + aggregate-исключение с `addSuppressed` — нормальный паттерн. Проверять: дублирование одинаковых блоков (AI-код любит копипастить toAdd/toUpdate для одного и того же upsert-метода), уникальность ключей, что retry после 5xx безопасен.

### 6. Качество тестов
- `verify(anyString())` там, где контракт — конкретное значение (`eq(savedPath)`) — тест проходит при регрессии. Требовать точное сопоставление + fixture, где сохранённое значение отличается от вычисляемого.
- Общий singleton-мок без `@BeforeEach`/`@AfterEach reset(...)` — зависимость от порядка тестов, утечка doThrow между сценариями.
- Новые error-пути покрыты регрессионными тестами (rollback-тест: зависимость падает после первой записи → проверяем, что всё откатилось).
- Gold-fixture тесты (`src/test/gold/**/before.yml` + `expected.yml`) — mdb-data стандарт для сервисных флоу.

### 7. AI-генерация кода — типовые артефакты
Двойное вычисление одного выражения (посчитали `changed`, а вернули повторный `!equals`), идентичные копипастные блоки, `log.debug` рядом с мёртвым дублем логики, многословие. Не блокировать, но перечислять в ревью.

### 8. Описание MR ≠ финальный код
AI-описание («Generated with Claude Code») не обновляется после правок по ревью. Сверять заявленный фикс с фактическим кодом; в вердикте отмечать расхождение — оно вводит в заблуждение будущих читателей MR.

## Калибровка (вердикты @vl.ershov — канон, не спорить повторно)

- **Осиротевшие секреты в Vault при удалении юзера — НЕ проблема.** «Пароли можно не удалять», «если на вольте останется его секрет — ничего страшного» (MR !498, дискуссии #2, #13). Не флагать orphaned secrets как High; best-effort удаление секрета — приемлемый контракт.
- **Имена юзеров с `?`/`#`** — не проблема: UI-валидация отсекает (MR !498, #15). Но sync-API идёт мимо UI — это различие учитывать, а не сам символ.
- Gena-ревью часто даёт 2–3 волны по 3–5 находок; часть — шум ( ложноположительные про URI/Unicode). Перепроверять его High-находки по факту поведения библиотеки, прежде чем тащить в вердикт.

## Формат ответа

1. Вердикт одной строкой (мёржить / мёржить с follow-up / просить правки).
2. «Костыльно» — нумерованный список с файлом:строкой и почему.
3. «Хорошо» — что сделано выше среднего (важно для калибровки ожиданий от автора).
4. Follow-up'ы, за которыми надо следить (с пометкой, заведены ли тикетом).
