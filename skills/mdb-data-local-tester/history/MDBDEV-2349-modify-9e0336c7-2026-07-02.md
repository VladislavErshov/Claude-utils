## Ключевые наблюдения

1. **`updateCruiseConfig` запустился, хотя `cruiseControl` полностью совпадает с БД.**
   В коде `hasCruiseControlDiff` проверяет `fieldChanged` по каждому полю:
   - `cruiseControlDc`: "dc" == "dc" → false
   - `autoRebalanceEnabled`: newValue=null → `fieldChanged` возвращает false
   - `autoRebalanceOnBrokerFailEnabled`: newValue=null → false
   - `replicationThrottleMb`: newValue=null → false
   - `jvmHeapSizeMb`: newValue=null → false

   Итого `hasCruiseControlDiff=false`. Но `cruiseUpdateConfigData != null` (потому что `cruiseControl` в modify-запросе != null) — workflow всё равно запускается. **Условие запуска `updateCruiseConfig` — `cruiseControl != null` в запросе, а не `hasCruiseControlDiff`**.

2. **`cruiseUpdateConfigData.cruiseControl` содержит null-поля.**
   `autoRebalanceEnabled=null, autoRebalanceOnBrokerFailEnabled=null, replicationThrottleMb=null, jvmHeapSizeMb=null`. Activity `upsertCruiseControlConfig` должно корректно обрабатывать null — иначе может записать null в PMS или упасть. В этом прогоне workflow завершился COMPLETED, значит null обработан. Но стоит проверить логи PMS-вызовов.

3. **`diskGb/lanInMb/lanOutMb=null`** в `cruiseUpdateConfigData` — `brokerResources=null` (нет broker resources diff). `upsertCruiseControlCapacity` должен сделать Skipping (как и описано в history MDBDEV-2349-cruise-capacity-2026-07-01.md).

4. **`updateControllerConfig` запустился с пустым `parameters={}`** — потому что `controllerConfig: null → {config: {}}` даёт diff. `heapSizeMB=2049` (строка "2049" в БД конвертируется в число). Рестарт 3 controller-инстансов (dc/kc/zc).

5. **`controllerJvmHeapSizeMb: "2049"` — строка.** В БД хранится как строка (вероятно legacy), в modify-запросе тоже строка. `hasControllerResourcesDiff` сравнивает `fieldChanged("2049", "2049")` → false. Работает, но значение 2049 нестандартное (обычно 1024/2048/4096). Стоит обратить внимание на валидацию.
