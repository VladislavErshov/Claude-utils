# I52237 — kafka-m2b-adtech-kafka: перенос партиций HC→RC и KC→UC (2026-09-10)

Полный перенос всех партиций с двух групп брокеров на новые ДЦ через
`kafka-reassign-partitions.sh`. Два захода одним паттерном за одну сессию.

## Кластер

`kafka-m2b-adtech-kafka`, 31 брокер, 5 ДЦ:

| ДЦ | Broker IDs | Было до |
|---|---|---|
| hc | 20001–20006 | ~68 GiB → **источник №1** |
| kc | 21001–21007 (21007 добавлен позже, почти пустой) | ~67 GiB → **источник №2** |
| pc | 22001–22006 | 9–13 GiB, не трогали |
| uc | 23001–23006 | пустые → **цель №2** |
| rc | 24001–24006 | пустые → **цель №1** |

111 топиков, 1111 партиций, все RF=3, каждая партиция имела ровно одну реплику в
каждом источнике. URP=0 перед обоими reassign. CC стоит на `1.cruise...rc` — не мешал.

## Схема маппинга

Требование: «распределение партиций по номерам брокеров как было» → **1:1 по индексу,
позиция в списке replicas сохраняется** (включая preferred leader), kc/pc реплики не трогаем.

- **HC→RC**: `2000N → 2400N` (ID+4000). Оба ДЦ по 6 брокеров — чистый 1:1.
- **KC→UC**: `2100N → 2300N` (ID+2000) для N=1..6; **21007 (7-й брокер) → round-robin**
  по 23001–23006 по счётчику партиций (его было всего 60 — брокер добавлялся позже).
  Расклад вышел: 23001=161, 23002=160, 23003=143, 23004=143, 23005=252, 23006=252.

ID узнавать заранее (`node.id` в `/opt/kafka/config/*.properties` по хосту из каждого ДЦ,
или `kafka-broker-api-versions.sh | grep "id:"` на bootstrap).

## Ход работы (паттерн)

1. Топология: `mcc --local -n infra -c <dc> instances "%.broker.<cluster>.<dc>%" -f xargs:host`.
2. Снимок: `kafka-topics --describe` + `kafka-log-dirs --describe` на 1.broker.kc —
   **детачем** (setsid nohup + done-маркер), потом python-парс.
3. Генерация JSON: python заменяет ID источника на ID цели **в той же позиции** списка;
   `log_dirs: ["any",...]`; разбивка на 5 батчей (~223 партиции) по (topic, partition).
4. URP-precondition, затем **все 5 батчей параллельно**, `--throttle 104857600` (100 MB/s)
   на каждый — множества партиций не пересекаются, конфликтов нет.
5. `--verify` по всем батчам циклом, счёт `is completed` / `is still in progress` до 0.
6. Финал: URP=0, размеры источников = 0.0, throttle-конфиги снялись **автоматически**
   (verify при завершении чистит `leader/follower.replication.throttled.replicas` —
   ручная чистка не понадобилась).

## Результаты

- **HC→RC**: 1111/1111 за ~6–7 мин (суммарно ~170 MB/s при 5×100 MB/s throttle).
  RC после: 9.3/11.1/10.4/10.3/8.9/7.9 GiB, hc = 0.0.
- **KC→UC**: 1111/1111 за ~4–5 мин. UC после: 8.0/7.5/9.1/9.6/11.0/8.0 GiB, kc = 0.0.
- URP=0 на всём протяжении, лидерство переехало автоматически (auto leader rebalance).

Размеры «после» меньше исходных на ~15% — retention подрезал логи во время окна переноса,
не потеря.

## Грабли

1. **Фразы verify в Kafka 4.x**: `Reassignment of partition X is completed.` и
   `is still in progress` — **НЕ** `completed successfully`. Грепы по старым фразам дают
   ложные нули.
2. **`kafka-log-dirs` JSON нельзя `json.load` целиком** — впереди INFO-строки AdminClient
   (и `{key=value}` внутри них → `JSONDecodeError: Extra data`). Парсить от первой строки,
   начинающейся с `{`.
3. **`kafka-topics --describe` выводит 2 строки на топик** (config-строка + партиции) —
   регекс по `Partition:\s+\d+` конфиг-строки не цепляет, но дедуп по (topic,partition)
   всё равно нужен.
4. **Долгие команды на хосте — только детач**: `setsid nohup bash job.sh </dev/null
   >/dev/null 2>&1 & sleep 5` — без sleep процесс умирает вместе с sshexec-сессией
   (см. MDBSUP-5291). Прогресс — по done-маркерам.
5. **mcc первый вызов часто падает** (`Connection closed by remote host` — печатается даже
   при успехе) — ретраи 3–5× с паузой; пустой вывод при grep-no-match — добавлять `; true`
   в конец remote-команды, иначе `&&`-цикл ретрая молчит.
6. **Локальные переменные в remote-скрипте** (`$K=...; $K/kafka-...`) — один раз попали
   в remote пустыми → `/kafka-reassign-partitions.sh: No such file`. Надёжнее: путь целиком
   захардкодить ИЛИ перед отправкой `cat`-нуть декодированный скрипт для проверки.
   base64-обёртка не спасает от собственной двойной подстановки при сборке команды.
7. **Cruise Control на кластере** — на время reassign не выключали, не помешал (self-healing
   не сработал, throttle-конфиги не переписал).
