# MDBSUP-5067 — vkcluster-kafka: кампания поднятия RF 2→3 на всех топиках + misr=2

**Дата**: 2026-09-02
**Кластер**: `vkcluster-kafka` (`eba4c8ec-ce96-4997-9e14-e83adaac1f71`), Kafka 3.8.0, KRaft,
160 брокеров (40 в каждом ДЦ ec/hc/kc/pc) + 3 контроллера. Критичность B, прод.
**Тикет**: MDBSUP-5067 (фичареквест от пользователя через L1). Учения INCALL-49801
(02.09.2026) — выполнять только после их завершения.

- 26 пользовательских топиков (+ internal). 16 уже RF=3, **10 топиков RF=2** (438 партиций):
  story_feed_v2 (120), video_card_views (30), bookmarks (60), story_publish (60),
  story_view (60), comments (60), search_video_indexing_online_ugc_videos_partners (16),
  search_video_playlists_indexing_online_ugc_partners (12),

  search_video_indexing_online_pugc_videos_partners (8).
- min.insync.replicas=1 был у 14 топиков (те же 10 + 4 offline_* RF=3).
- Схема реплик RF=2-топиков: пары в {kc, pc, ec}, **hc не задействован вообще**.
- Учения к моменту работы закончились: все 160 брокеров `state=RUNNING` (mcc instances
  по каждому ДЦ), URP=0, offline-партиций нет. NB: сразу после учений URP был 83 —
  кластер догнался сам, перед reassign обязательно дождаться URP=0.

## Что сделано

1. **Broker id → ДЦ**: `kafka-configs.sh --describe --entity-type brokers --all` — парсить
   строку `All configs for broker <id> are:` (id = $5) + `broker.rack=<dc>`. Не верить
   `broker.id` в server.properties — там рендер-заглушка `broker.id=0`.
2. **Генератор** (python3.8 на брокере, `/tmp/gen_reassign.py`): для каждой из 438 партиций
   третья реплика в ДЦ с минимумом текущих реплик (→ hc: 292, ec: 146), брокер — least-loaded
   по общему числу реплик в кластере (greedy, `load[b]+assigned[b]`), preferred leader
   сохранён (новая реплика аппендится в конец). Все пары исходно cross-DC (0 same-DC).
3. **Reassign**: `--execute --throttle 104857600` упал; повтор `--execute` без throttle —
   `Successfully started` по всем 438. Rollback-JSON — `/tmp/reassign_rollback.log` на
   1.broker...ec.
4. **Ход**: 183/438 за ~1 мин, 362 за 3 мин, хвост — жирный story_view (44 партиции),
   всего ~20 мин до `--verify`: 438 completed, in progress 0.
5. **misr=2** после завершения reassign: `kafka-configs.sh --alter --add-config
   min.insync.replicas=2` на 14 топиках — все «Completed updating config».
6. **Финал**: 26 топиков, `ReplicationFactor: 3` ×26, `min.insync.replicas=2` ×26, URP=0,
   offline=0.

## Новая грань известной грабли «--execute с throttle падает»

В known_issues (#4) задокументирован TimeoutException на incrementalAlterConfigs. Здесь
вариант: `InvalidRequestException: Dynamic thread count update validation failed for
num.replica.fetchers=8, value should not be greater than double the current value 1`.
Лечение то же — повторить `--execute` без throttle. Записано в known_issues.md.

## Грабли сессии

- `kafka-topics.sh --list` (и некоторые вызовы) пишут AdminClientConfig-dump **в stdout** —
  в счетчики/`comm` попадает мусор. Фильтровать `grep -v '[[:space:]]'` / `grep -v '='`,
  либо `2>/dev/null` недостаточно (dump идёт в stdout, не stderr).
- awk-извлечение значения из `match()`: `min.insync.replicas=` — 20 символов, сдвиг
  `RSTART+19` оставляет «=» в значении — сравнение со «2» всегда false. Считать офсет
  по фактической длине.
- Заливка скрипта ~3.5KB base64 одним sshexec → `431 Request Header Fields Too Large`
  (лимит мягче заявленных 8KB). Порог чанкования — где-то между 2.7KB (ок) и 4.7KB
  (431); надёжнее сразу expect-чанки по 800 символов.
- Long describe-вывод парсить awk с `-F'\t'` — заголовки и партиции таб-разделены,
  формат полей `Topic: X`/`PartitionCount: N`/`Replicas: a,b,c`.
